Deckhouse Development Portal (DDP) устанавливается модулем `development-platform` в кластере Deckhouse Platform (DP).

Для разных сценариев установки выделите следующие CPU, память и диск:

| Профиль | DDP: CPU / память | PostgreSQL: CPU / память / диск                | Redis: CPU / память / диск                     | ClickHouse: CPU / память / диск                |
| --- | --- |------------------------------------------------|------------------------------------------------|------------------------------------------------|
| Демо-установка | 4 CPU / 8 ГБ | 2 CPU / 4 ГБ / 20 ГБ | 1 CPU / 2 ГБ / 10 ГБ | 2 CPU / 8 ГБ / 50 ГБ |
| 10 пользователей | 8 CPU / 32 ГБ | 2 CPU / 8 ГБ / 32 ГБ                           | 2 CPU / 4 ГБ / 16 ГБ                           | 4 CPU / 16 ГБ / 64 ГБ                          |
| 100 пользователей | 16 CPU / 32 ГБ | 2 CPU / 16 ГБ / 64 ГБ                          | 2 CPU / 8 ГБ / 16 ГБ                           | 4 CPU / 16 ГБ / 64 ГБ                          |
| 200 пользователей | 16 CPU / 64 ГБ | 2 CPU / 16 ГБ / 64 ГБ                          | 2 CPU / 16 ГБ / 32 ГБ                          | 4 CPU / 16 ГБ / 128 ГБ                         |
| 500 пользователей | 32 CPU / 64 ГБ | 4 CPU / 64 ГБ / 256 ГБ                         | 2 CPU / 32 ГБ / 64 ГБ                          | 4 CPU / 16 ГБ / 256 ГБ                         |
| 1000 пользователей | 32 CPU / 128 ГБ | 16 CPU / 64 ГБ / 512 ГБ                        | 2 CPU / 32 ГБ / 128 ГБ                         | 4 CPU / 32 ГБ / 512 ГБ                         |

Бюджет DDP включает API, веб-интерфейс, платформенный AI-агент и воркеры.
Для демо-установки рекомендуется режим `managed` для баз данных, для остальных профилей — режим `external`.

Бюджет для каждой внешней базы данных указан на один сервер.
Он рассчитан по сценариям и допущениям ниже.
CPU рассчитан по частоте и стоимости операций, память — по рабочему набору данных и параллельности,
диск — по накопленным данным и месту для обслуживания.
Дополнительно учтите ресурсы всех реплик, резервного копирования и служебных компонентов.

Расчёт охватывает первые 180 дней эксплуатации.
Как получены значения, описано [в расчёте CPU и памяти](#расчёт-cpu-и-памяти-баз-данных)
и [в расчёте дискового пространства](#расчёт-дискового-пространства).

Бюджет портала — это свободные ресурсы для подов DDP.
Дополнительно учтите потребление DP, операционной системы, других приложений,
временных подов при обновлении и запас на отказ узлов.

Требуется DP версии 1.72 или новее с доступным модулем `development-platform`,
модуль [user-authn](/modules/user-authn/) и постоянное хранилище для баз данных в кластере.
Порядок установки и подключения баз данных приведён [в руководстве по установке](install/).

## Демо-установка

Сценарий демо-установки предполагает одного пользователя, небольшой каталог и выполнение одного-двух процессов одновременно.
Для демо-установки используйте PostgreSQL, Redis и ClickHouse в режиме `managed`.
До установки включите модули DP [`managed-postgres`](/modules/managed-postgres/configuration.html#enable), [`managed-valkey`](/modules/managed-valkey/configuration.html#enable) и [`managed-clickhouse`](/modules/managed-clickhouse/configuration.html#enable).
В этом режиме Redis заменяется совместимым с ним Valkey.
ClickHouse хранит историю параметров, доступную для демонстрации возможностей портала.

Для DDP вместе с managed-экземплярами баз данных выделите следующие ресурсы в уже работающем кластере DP:

| Параметр | Значение |
| --- | --- |
| Пользовательская нагрузка | 1 пользователь |
| CPU | 9 CPU с учётом managed-экземпляров |
| Память | 22 ГБ с учётом managed-экземпляров |
| Одновременно выполняющиеся процессы | 1–2 |
| Постоянный диск | 80 ГБ: PostgreSQL — 20 ГБ, Valkey — 10 ГБ, ClickHouse — 50 ГБ |
| `workers.replicas` | `1` |
| `workers.maxTasks` | `5` |
| ClickHouse | Включён, режим `managed` |

Бюджет компонентов портала для демо составляет 4 CPU и 8 ГБ памяти.
Managed-экземпляры по умолчанию добавляют 5 CPU по сумме лимитов и 14 ГБ памяти.
Сумма составляет 9 CPU и 22 ГБ памяти.
При `coreFraction: 50` для PostgreSQL и `coreFraction: "50%"` для Valkey и ClickHouse
гарантированный запрос CPU managed-экземпляров составляет суммарно 2,5 CPU.
Бюджет рассчитан по полным лимитам CPU.

При двух процессах с двумя активными шагами каждый воркер сможет выполнять четыре задачи процессов
и одну дополнительную фоновую задачу одновременно.
Ресурсы самой DP, образы контейнеров и временный диск добавляются к этому бюджету.

Добавьте следующие настройки в ModuleConfig `development-platform`. Остальные параметры установки не меняйте:

```yaml
spec:
  settings:
    postgres:
      mode: managed
    redis:
      mode: managed
    clickhouse:
      mode: managed
    workers:
      replicas: 1
      maxTasks: 5
```

В примере используются ресурсы managed-экземпляров по умолчанию.
Чтобы изменить их, задайте CPU в `instance.cpu`, память в `instance.memory`
и размеры томов в `instance.persistentVolumeClaim.size`, затем пересчитайте суммарный бюджет.
Класс managed-экземпляра должен допускать выбранные CPU, память и размеры томов.
Параметры экземпляров описаны [в руководстве по установке с managed-экземплярами](install/#установка-с-managed-экземплярами).

При увеличении каталога, числа одновременно выполняющихся задач или активных пользователей
перейдите к профилям с пользовательской нагрузкой.

## Сценарии нагрузки

Выберите профиль по ожидаемому числу активных пользователей и объёму каталога.
В примерах один выполняющийся процесс имеет два одновременно активных шага,
каждый из которых занимает одно место воркера.
Фоновые задачи включают синхронизации источников данных, проверки статуса и другие операции из общей очереди:

| Параметр сценария | 10 пользователей | 100 пользователей | 200 пользователей | 500 пользователей | 1000 пользователей |
| --- | --- | --- | --- | --- | --- |
| Активные (одновременно работающие) пользователи | 2 | 20 | 40 | 100 | 200 |
| Одновременно выполняющиеся процессы | 2 | 5 | 10 | 15 | 20 |
| Задачи воркеров из процессов | 4 | 10 | 20 | 30 | 40 |
| Одновременно выполняющиеся фоновые задачи | 6 | 10 | 20 | 30 | 40 |
| Всего одновременно выполняющихся задач | 10 | 20 | 40 | 60 | 80 |
| Сущности в каталоге | 1000 | 10 000 | 20 000 | 50 000 | 100 000 |
| Ресурсы каталога, создающие события | 10 | 20 | 40 | 80 | 100 |
| `workers.replicas` | `1` | `2` | `4` | `6` | `8` |
| `workers.maxTasks` | `10` | `10` | `10` | `10` | `10` |

Выбирайте профиль по всем параметрам сценария вместе.
Число зарегистрированных пользователей влияет на накопление запусков процессов,
а число активных пользователей — на частоту запросов к API и базам данных.
Установка на 10 пользователей с частыми синхронизациями большого каталога может потребовать больше воркеров, чем профиль на 100 пользователей.
Число сущностей само по себе также не задаёт необходимую память.
Учитывайте размер параметров и объём одной синхронизации.

API, веб-интерфейс и платформенный AI-агент работают по одной реплике в каждом профиле.
Количество воркеров повышает параллельность фоновых задач.
Для профиля на 1000 пользователей отдельно проверьте производительность API и баз данных.
Увеличение числа воркеров не повышает производительность всех компонентов одновременно.

## Допущения расчёта

Профили рассчитаны для следующего объёма данных и активности.
При изменении этих параметров пересчитайте соответствующую часть бюджета:

| Параметр | Значение в расчёте |
| --- | --- |
| Чтение данных | 1 пакет запросов в секунду на активного пользователя в пике. 90% пакетов — чтение каталога и событий, 10% — поиск по всему каталогу |
| Просмотр истории параметров | 10% активных пользователей одновременно. До 1 запроса в секунду на такого пользователя |
| Запуски процессов | 2 запуска на пользователя в рабочий день |
| Горизонт накопления запусков | 180 календарных дней, приблизительно 129 рабочих дней |
| Размер данных одного запуска | 256 КБ суммарно для процесса, его действий, контекста, результатов и журналов |
| Размер текущей сущности | 2 КБ |
| Изменения сущности | 5 изменений в сутки, каждое создаёт событие и запись истории параметра |
| Размер полного события | 8 КБ, включая старое и новое состояние сущности |
| Хранение событий в PostgreSQL | 4 дня и до 1 дня ожидания очередной очистки |
| Потоки событий Redis | Около 10 000 событий на каждый ресурс каталога. Новые события продлевают срок жизни потока |
| Пик синхронизации | В 100 раз выше средней суточной скорости изменений |
| Размер записи истории параметра | 1 КБ до сжатия |
| Хранение истории параметров | 180 дней |
| Очередь задач | До 10 000 задач по 16 КБ |
| Временный результат задачи | 64 КБ, хранение 3 минуты |
| Длительность задачи для расчёта обмена | 5 секунд. Число завершений в секунду равно числу мест воркеров, делённому на 5 |
| Автоматизации по событиям | До 2 получателей на событие. Задачи, которые они создают, входят в общий предел параллельности |
| Свободный диск | 30% после размещения данных и запаса на обслуживание |

Размеры записей являются параметрами профиля и включают полезные данные.
Индексы, служебные структуры, кеши и временные копии расчёт учитывает дополнительными коэффициентами ниже.
Записи процессов и действий продолжают накапливаться после выбранного горизонта.
Планируйте дальнейшее расширение диска.

## Ресурсы компонентов DDP

Для профилей на 10–1000 пользователей бюджет складывается из следующих ресурсов компонентов.
В таблице указаны приблизительные значения на один экземпляр до округления:

| Компонент | CPU | Память |
| --- | --- | --- |
| API (`backend`) | 4 CPU | 8,59 ГБ |
| Веб-интерфейс (`frontend`) | 1 CPU | 2,15 ГБ |
| Платформенный AI-агент (`agent`) | 1 CPU | 1,07 ГБ |
| Один воркер (`worker`) | 2 CPU | 8,59 ГБ |

Для `N` воркеров сумма ресурсов API, веб-интерфейса, AI-агента и воркеров составляет
`6 + 2 × N` CPU и около `11,81 + 8,59 × N` ГБ памяти.
Например, для двух воркеров сумма для портала равна `6 + 2 × 2 = 10` CPU
и примерно `11,81 + 8,59 × 2 = 28,99` ГБ памяти.
После округления вверх бюджет составит 16 CPU и 32 ГБ памяти без баз данных.

## Расчёт CPU и памяти баз данных

Расчёт CPU исходит из пиковой частоты операций и их стоимости в процессорном времени.
Расчёт включает двукратный запас на различия CPU и целевую загрузку до 50%.
Поэтому потребление `Σ(операций в секунду × мс CPU на операцию) / 1000`
умножается на 4, после чего округляется вверх до степени двойки.

Стоимость типичных операций принята по измерениям запросов и команд с синтетическими данными.
Для запросов истории использована история одной сущности из 900 записей за 180 дней:

| Операция | Стоимость операции в расчёте |
| --- | --- |
| PostgreSQL: пакет чтения каталога и событий | 2 мс. Для запросов связанных объектов и проверки доступа — 4 мс |
| PostgreSQL: поиск по 100 000 сущностей | 40 мс. Масштабируется пропорционально размеру каталога |
| PostgreSQL: обновление сущности с историей и событием | 1 мс, с запасом на размер события 8 КБ |
| Redis: запись или доставка события 8 КБ | 0,03 мс |
| Redis: короткая команда координации | 0,01 мс |
| Redis: обмен задачей и результатом между воркером и бэкендом | 0,4 мс, с запасом на отдельные команды и дополнительные обращения |
| ClickHouse: запрос страницы, окна истории или состояния на дату | 16 мс |
| ClickHouse: вставка записи с запасом на слияния | 0,004 мс на запись |

Большие ответы, другие виды поиска и более частые запросы изменяют стоимость операций.
Для дисков используйте SSD. Задержки чтения и записи также влияют на время ответа.

### CPU и память PostgreSQL

Расчёт CPU учитывает чтения пользователей, поиск и пиковый поток изменений от синхронизаций.
Минимальный бюджет в модели составляет 2 CPU.
Например, в профиле на 1000 пользователей работают 200 активных пользователей
и поступает до 579 изменений сущностей в секунду в пике.
Расчётное потребление составляет около 2,1 CPU.
После умножения на 4 и округления бюджет равен 16 CPU.

Рабочий набор памяти включает текущий каталог, события за 5 дней
и данные запусков за последние 30 календарных дней, приблизительно 22 рабочих дня.
Объём рабочего набора умножается на 1,5 для индексов и кеширования.
Расчёт дополнительно добавляет служебный запас 2 ГБ,
32 МБ на чтение каждого активного пользователя
и по 8 МБ на каждое из 10 параллельных обновлений одной фоновой задачи.
Минимальный бюджет памяти в модели составляет 8 ГБ.
Учтите параллельные операции и соединения также в настройках PostgreSQL.
PostgreSQL расходует память сортировок и хеш-операций на каждую операцию, как описано
[в документации PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-resource.html).

### CPU и память Redis

В расчёт CPU входят следующие операции Redis:

- публикация событий;
- чтение событий и их подтверждение автоматизациями;
- постановка задач в очередь;
- чтение новых и ожидающих задач;
- подтверждение и удаление выполненных задач;
- установка и продление блокировок;
- публикация и получение результатов.

На событие учтены запись, продление срока хранения и чтение с подтверждением двумя получателями.
Расчёт дополнительно учитывает до 35 коротких команд в секунду на воркер
и до 2 обращений в секунду на активного пользователя.
В профиле на 1000 пользователей это около 4500 команд в секунду.
Минимальный бюджет в модели равен 2 CPU, включая запас на сохранение данных.
Для указанных частот расчёт CPU остаётся в этом бюджете.

Для памяти расчёт учитывает полные потоки: `число ресурсов каталога × 10 000 событий`.
Лимит действует на каждый поток ресурса отдельно. Redis соблюдает его приблизительно.
Новое событие продлевает срок жизни всего потока.
Срок хранения событий в PostgreSQL не ограничивает возраст событий активного потока Redis.
При изменении `events.streamMaxLen` пересчитайте объём потоков.
При значении `0` или меньше ограничение длины отключается.

К событиям расчёт добавляет очередь из 10 000 задач и результаты завершённых задач за 3 минуты.
Общий объём умножается на 1,3 для структур Redis
и ещё на 2 для временной копии при сохранении данных.
Расчёт добавляет 0,5 ГБ служебного запаса и по 1 МБ буферов на активного пользователя.
Минимальный бюджет памяти в модели равен 4 ГБ.

В профиле на 1000 пользователей полезные данные занимают около 8,54 ГБ.
Расчёт с запасами даёт около 23 ГБ и округляется до 32 ГБ.
Влияние сохранения данных описано [в документации Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

### CPU и память ClickHouse

Расчёт CPU учитывает запросы истории, восстановление параметров на дату,
вставку изменений и фоновые слияния.
При 20 запросах истории в секунду и пиковых 579 вставках в секунду
расчётное потребление составляет около 0,32 CPU.
После умножения на 4 потребление остаётся ниже минимального бюджета модели в 4 CPU.
Поэтому CPU в указанных профилях одинаковый.

Расчёт памяти складывается из 8 ГБ служебного запаса,
0,5 ГБ на каждого пользователя, который одновременно просматривает историю,
и кеша размером 25% объёма истории за последний месяц.
Расчёт дополнительно учитывает четыре копии пакета из 10 000 записей при обработке вставки.
Минимальный бюджет памяти в модели равен 16 ГБ.
Для профиля на 1000 пользователей расчёт даёт около 22 ГБ и округляется до 32 ГБ.
Расход памяти на чтение и слияния зависит от запроса, а не только от числа возвращённых строк.
Зависимость ресурсов от запросов описана
[в рекомендациях ClickHouse](https://clickhouse.com/docs/guides/oss/best-practices/sizing-and-hardware-recommendations).

Для нескольких серверов базы данных умножьте бюджет на их число.
Если сервер обслуживает другие приложения, добавьте ресурсы для DDP к бюджетам этих приложений.

## Исходные данные для расчёта

Основные источники нагрузки различаются по компонентам.
Перед выбором профиля соберите следующие параметры:

| Источник нагрузки | Параметры нагрузки | Основной потребитель |
| --- | --- | --- |
| Работа пользователей | Число активных пользователей, частота запросов, поиск и фильтрация каталога, число открытых виджетов | API и PostgreSQL. Виджеты также обращаются к внешним системам |
| Выполнение процессов | Число одновременно выполняющихся процессов, параллельные ветки, длительность действий, объём контекста и результатов | API хранит состояние выполнения. Воркеры выполняют задачи. PostgreSQL хранит записи запусков |
| Синхронизация каталога | Число источников данных, расписание, число и размер объектов в одной выборке, сопоставление сущностей и создание связей | Память и CPU воркеров, PostgreSQL, внешние API |
| Проверки статуса | Число сущностей и правил, периодичность, длительность проверок | Воркеры и внешние системы |
| История параметров | Число изменений, размер старого и нового значения, срок хранения, запросы за большие периоды | PostgreSQL до переноса, ClickHouse после переноса, фоновые операции воркеров |
| События и обмен задачами | Частота и размер событий, число потоков, длина очереди, блокировки, объём результатов и число завершений задач | Redis: CPU, память и диск. PostgreSQL хранит события |
| Журналы выполнения | Объём записей запусков и детализация журналов | PostgreSQL и диск |
| Шаблоны и репозитории | Размер пакетов и репозиториев, число одновременных операций | CPU, память и временный диск воркеров |
| AI | Число параллельных запусков, длина диалога, размер ответов инструментов, время ответа провайдера | API, AI-агент, воркеры и PostgreSQL |

При синхронизации DDP обрабатывает коллекцию полученных объектов и загружает сущности соответствующего ресурса каталога.
Крупная выборка повышает расход памяти даже при небольшом числе пользователей.
Уменьшение числа параллельных синхронизаций снижает их одновременное потребление памяти.

Ресурсы сервиса AI-модели и GPU при самостоятельном размещении модели учитывайте отдельно.
Для рабочих пространств отдельно просуммируйте запросы CPU, памяти и хранилища из шаблонов всех одновременно запущенных рабочих пространств.
Добавьте ресурсы задач подготовки.
Бюджеты профилей включают постоянные компоненты портала.
Рабочие пространства, среды разработки, CI-задачи и приложения, которые создают через DDP, добавляются к бюджетам профилей.

## Расчёт количества воркеров

Один воркер обрабатывает до `workers.maxTasks` задач из очереди одновременно.
Общий предел параллельности равен `workers.replicas × workers.maxTasks`.
В профилях используется `workers.maxTasks: 10`, поэтому для 10, 20, 40, 60 и 80 задач
профили используют 1, 2, 4, 6 и 8 воркеров.
Настройка описана [в разделе «Воркеры»](architecture/workers/).

Число выполняющихся процессов и число занятых мест воркеров различаются.
Один процесс с параллельными ветками может занимать несколько мест.
Процесс не занимает место воркера, пока ждёт подтверждения пользователя.
В общий расчёт включайте также синхронизации, проверки статуса, вызовы MCP и запуски AI-агентов.
Запуск AI-агента из процесса занимает место до завершения задачи.
Перенос истории в ClickHouse и её очистка выполняются дополнительно к задачам очереди
и также потребляют ресурсы воркеров.

Для постоянного потока задач оцените среднее число занятых мест как сумму `λ × t` по всем типам задач.
Здесь `λ` — число поступающих задач в секунду, `t` — средняя длительность задачи в секундах.
Например, 2 задачи в секунду длительностью 5 секунд занимают в среднем 10 мест.
При `workers.maxTasks: 10` такой поток полностью загружает один воркер.
Добавьте запас параллельности для пиков и длительных задач.
Пределы параллельности профилей не задают производительность в задачах в секунду.

Увеличение `workers.maxTasks` повышает одновременное потребление памяти одним подом
и число обращений к PostgreSQL и внешним системам.
Например, одна синхронизация может обновлять параметры до 10 сущностей параллельно.
При десяти таких задачах по разным ресурсам каталога в одном воркере возможно до 100 параллельных операций обновления параметров.
Перед увеличением параллельности проверьте соединения с PostgreSQL и ограничения внешних API.

## Расчёт дискового пространства

В демо-установке используются следующие размеры постоянных томов managed-экземпляров:

| Компонент | Размер тома в демо-установке |
| --- | --- |
| PostgreSQL | 20 ГБ |
| Valkey | 10 ГБ |
| ClickHouse | 50 ГБ |
| Всего | 80 ГБ |

Эти размеры заданы по умолчанию для managed-экземпляров.
Они не увеличиваются при изменении числа пользователей или воркеров.
При росте данных увеличьте тома или перейдите к профилю с выделенными базами данных.
При размещении баз данных в кластере дополнительно учтите репликацию хранилища и резервные копии.

В профилях на 10–1000 пользователей диск каждой базы данных должен быть не меньше её тома в демо-установке.
После округления вверх до степени двойки минимальные бюджеты составляют
32 ГБ для PostgreSQL, 16 ГБ для Redis и 64 ГБ для ClickHouse.
Для каждого профиля выберите больший из минимального бюджета и бюджета по расчёту ниже.

### Диск PostgreSQL

Объём полезных данных `D` складывается из:

- текущего каталога: `число сущностей × 2 КБ`;
- событий: `число сущностей × 5 изменений × 5 дней × 8 КБ`;
- запусков процессов и действий: `число пользователей × 2 запуска × 129 рабочих дней × 256 КБ`;
- очереди переноса истории за сутки: `число сущностей × 5 изменений × 1 КБ`.

В модели `D` удваивается для индексов и места, которое расходуют обновления записей.
Для журнала предзаписи (WAL) расчёт добавляет больший из двух запасов:
8 ГБ или двукратный суточный объём записываемых данных.
Суточный объём записи складывается из изменений каталога
`число сущностей × 5 × (2 + 8 + 1) КБ`
и данных запусков `число пользователей × 2 × 256 КБ` в рабочий день.
Бюджет диска равен `(2 × D + запас WAL) / 0,7`, округлённым вверх до степени двойки.
Минимальный бюджет составляет 32 ГБ и покрывает том 20 ГБ из демо-установки.
Деление на 0,7 оставляет 30% свободного места.

Для 1000 пользователей полезные данные занимают около 88,83 ГБ.
С учётом индексов, обновлений, WAL и свободного места требуется около 271 ГБ.
После округления бюджет составляет 512 ГБ.

Этот расчёт охватывает данные заданного сценария.
Диалоги AI, крупные контексты процессов, дополнительные связи и более подробные логи увеличивают объём.

Срок хранения событий `events.ttl`, по умолчанию `96h`, не задаёт срок хранения всех данных DDP.
180 дней для запусков процессов — горизонт планирования, а не автоматический срок удаления.

Если перенос истории в ClickHouse задерживается больше суток,
увеличьте запас места под очередь в PostgreSQL пропорционально времени задержки.
Для WAL также учтите фактические настройки и возможное отставание реплик.

### Диск Redis

Полезный объём `B` включает потоки событий, очередь задач и временные результаты.
Как рассчитать их объём, описано [в разделе о памяти Redis](#cpu-и-память-redis).
Бюджет диска предусматривает три копии объёма `1,3 × B`:
сохраняемые данные и место для снимка, журнала AOF и его перезаписи.
Расчёт дополнительно добавляет час записей при пиковой частоте событий и завершений задач.

При `p` событиях и `q` завершениях задач в секунду часовой объём записи равен
`(p × 8 КБ + q × (16 + 64) КБ) × 3600`.
Бюджет диска равен `(3 × 1,3 × B + часовой объём записи) / 0,7`,
округлённым вверх до степени двойки, с минимумом 16 ГБ, который покрывает том 10 ГБ из демо-установки.
Для профиля на 1000 пользователей расчёт даёт около 79 ГБ и округляется до 128 ГБ.

Бюджет рассчитан для включённого сохранения данных с регулярной перезаписью журнала AOF.
При другой политике RDB/AOF, редкой перезаписи или длительной записи на пиковой скорости
пересчитайте место под журнал AOF и временные файлы.
Диск Redis не заменяет память, поскольку потоки, очереди и результаты должны помещаться в RAM.

### Диск ClickHouse

Объём истории равен `E × Δ × T × S`, где:

- `E` — число сущностей;
- `Δ` — число изменений отдельных параметров одной сущности в сутки;
- `T` — срок хранения в сутках;
- `S` — средний размер записи об изменении.

Повторная синхронизация значения, которое не изменилось, не считается изменением параметра.
По умолчанию история хранится 180 дней.
Срок задаёт параметр `clickhouse.propertyHistory.retentionDays`.

В профилях приняты 5 изменений параметров на сущность в сутки и размер записи 1 КБ до сжатия.
Выигрыш от сжатия в расчёте не учитывается.
Бюджет диска включает 16 ГБ базового запаса,
место для истории и её временной копии при обслуживании, а также 30% свободного пространства.
Итоговый бюджет равен `(16 + 2 × объём истории) / 0,7` ГБ,
округлённым вверх до степени двойки, с минимумом 64 ГБ, который покрывает том 50 ГБ из демо-установки:

| Число сущностей | Число записей истории за 180 дней | Объём записей до сжатия | Бюджет диска ClickHouse |
| --- | --- | --- | --- |
| 1000 | 900 000 | Около 0,92 ГБ | 64 ГБ |
| 10 000 | 9 000 000 | Около 9,2 ГБ | 64 ГБ |
| 20 000 | 18 000 000 | Около 18,4 ГБ | 128 ГБ |
| 50 000 | 45 000 000 | Около 46,1 ГБ | 256 ГБ |
| 100 000 | 90 000 000 | Около 92,2 ГБ | 512 ГБ |

Выберите том не меньше расчётного бюджета.
При изменении частоты изменений, размера записей или срока хранения пересчитайте бюджет диска.
Сжатие уменьшает фактический объём данных.
Слияния частей и отставание очистки увеличивают временное потребление диска.

### Временный диск DDP

На узлах отдельно выделите временное дисковое пространство.
API и воркеры используют временные тома `emptyDir`, в том числе для кеша и работы с репозиториями.
Запрос модуля на `ephemeral-storage` составляет около 0,052 ГБ на контейнер и покрывает только логи.
Клонируемые репозитории, пакеты шаблонов и образы контейнеров в этот запрос не входят.
