Реестр шаблонов подключает источники образов (OCI), синхронизирует каталог шаблонов и позволяет создавать и обновлять микросервисы из шаблонов на главной странице.

Настройка выполняется в разделе «Администрирование» → «Реестр шаблонов».

{{< alert level="info" >}}
Для процессов создания и обновления примените набор данных [«Реестр шаблонов микросервисов»](../datasets/#реестр-шаблонов-микросервисов). В каталоге должны быть ресурсы систем и микросервисов.
{{< /alert >}}

## Быстрый старт

1. Добавьте источник образов на вкладке «Источники» и сохраните.
1. На вкладке «Настройки» включите синхронизацию.
1. Запустите синхронизацию на вкладке «Запуски синхронизации».
1. Шаблоны появятся во вкладке «Шаблоны» и в разделе главной «Создать микросервис».

## Создание своего шаблона

Шаблон — это каталог файлов (пакет), который публикуется в OCI-реестр образов и подхватывается синхронизацией реестра шаблонов. В файлах пакета используются Go-шаблоны с подстановкой значений, например `{{ .slug }}` и `{{ .name }}`.

### Структура пакета

В корне каталога обязательны:

| Файл             | Назначение                                                                 |
|------------------|----------------------------------------------------------------------------|
| `template.yaml`  | Манифест шаблона (идентификатор, язык, стратегия обновления)               |
| `values.yaml`    | Значения по умолчанию для рендера. При синхронизации сохраняются в каталоге и показываются в окне создания микросервиса |
| `.templateignore` | Пути, которые не копируются в репозиторий сервиса (обычно сам манифест)   |

Остальные файлы — каркас сервиса (CI, Dockerfile, код, манифесты деплоя и т. д.). Имена файлов и каталогов тоже могут содержать шаблоны, например `cmd/{{ .slug }}/main.go`.

В пакет не включайте каталог `.ddp/` — он появляется только в репозитории сервиса. Подробнее — в разделе [«Lock-файл сервиса»](#lock-файл-сервиса).

Пример `template.yaml`:

```yaml
id: go-service
name: Go service
description: Каркас Go-сервиса с Dockerfile, Helm и GitLab CI
language: go
tags:
  - go
  - helm
update:
  strategy: selective_additive
  overwrite:
    - .gitlab-ci.yml
    - deploy/**
    - go.mod
  addIfMissing:
    - .dockerignore
```

Пример `values.yaml`:

```yaml
slug: go-service
name: Go service
```

Пример `.templateignore`:

```text
template.yaml
.templateignore
```

### Поля `template.yaml`

| Поле            | Обязательность | Описание                                                                                          |
|-----------------|----------------|---------------------------------------------------------------------------------------------------|
| `id`            | **да**         | Идентификатор шаблона (`a-z`, цифры, `-`). Должен совпадать с именем репозитория в OCI после префикса |
| `name`          | **да**         | Отображаемое название                                                                             |
| `language`      | **да**         | `go`, `vue`, `typescript`, `python`, `java` или `other`                                           |
| `update`        | **да**         | Настройки обновления; допускается `{}` (тогда стратегия по умолчанию — `selective`)               |
| `description`   | нет            | Краткое описание                                                                                  |
| `tags`          | нет            | Теги для фильтрации в галерее                                                                     |
| `minDdpVersion` | нет            | Минимальная версия платформы; при более старой сборке шаблон получит статус «недоступна»          |

Версия шаблона задаётся **тегом** в OCI при публикации (`1.2.3`), а не полем в `template.yaml`. Префикс `v` в теге не используется.

### Стратегии обновления

Стратегия из `update.strategy` применяется только при обновлении сервиса. При создании всегда рендерится весь пакет.

| Стратегия            | В интерфейсе                 | Поведение                                                                   |
|----------------------|------------------------------|-----------------------------------------------------------------------------|
| `selective`          | «Выборочная»                 | Перезаписывает только пути из `overwrite`                                   |
| `additive`           | «Добавление»                 | Добавляет пути из `addIfMissing`, если их ещё нет в репозитории             |
| `selective_additive` | «Выборочная и добавление»    | Сначала `overwrite`, затем `addIfMissing`                                   |
| `full`               | «Полная»                     | Перезаписывает все совпадающие файлы пакета                                 |
| `merge`              | «Слияние»                    | Трёхсторонний merge для путей из `overwrite`; конфликт прерывает обновление |

Для `selective`, `merge` и `selective_additive` список `overwrite` должен быть непустым. Для `additive` и `selective_additive` — непустой `addIfMissing`. Файлы вне этих списков при обновлении не удаляются.

В `overwrite` указывайте файлы, которыми владеет платформа (CI, манифесты деплоя). То, что правят команды сервиса, оставляйте в `addIfMissing` или вне списков.

### Команды `ddp-template`

Утилита `ddp-template` проверяет пакет, собирает архив, публикует и скачивает шаблоны из OCI-реестра.

| Команда                          | Назначение                                                                               |
|----------------------------------|------------------------------------------------------------------------------------------|
| `ddp-template lint <path>`       | Проверка `template.yaml`, `values.yaml`, `.templateignore` и dry-run рендера             |
| `ddp-template pack <path>`       | Сборка `tar.gz` корня пакета (без `.git`)                                                |
| `ddp-template publish <path>`    | Lint, упаковка и push в OCI; печатает JSON с `templateId`, `version`, `ociRef`, `sha256` |
| `ddp-template pull <templateId>` | Скачать и распаковать опубликованный пакет                                               |
| `ddp-template render <packPath>` | Локальный рендер, в том числе симуляция стратегии обновления                             |

#### `lint`

```bash
ddp-template lint ./my-template
ddp-template lint ./my-template --expect-id my-template --render-smoke --strict
```

| Флаг           | Описание                                                                 |
|----------------|--------------------------------------------------------------------------|
| `--expect-id`  | Требовать, чтобы `id` в `template.yaml` совпадал с указанным значением   |
| `--no-render`  | Не выполнять dry-run рендер                                              |
| `--render-smoke` | Рендер только со значениями из `values.yaml` (быстрая проверка в CI)   |
| `--strict`     | Считать предупреждения ошибками                                          |

Коды выхода: `0` — без замечаний, `1` — ошибки (или предупреждения при `--strict`), `2` — есть предупреждения.

#### `pack`

```bash
ddp-template pack ./my-template --version 0.1.0
ddp-template pack ./my-template --output ./my-template-0.1.0.tar.gz
```

| Флаг        | Описание                                                                  |
|-------------|---------------------------------------------------------------------------|
| `--version` | Semver для имени архива по умолчанию (`{id}-{version}.tar.gz`); обязателен, если не задан `--output` |
| `--output`  | Путь к архиву                                                             |

#### `publish`

```bash
ddp-template publish ./my-template --version 0.1.0 \
  --registry registry.example.org \
  --repository-prefix ddp-templates
```

| Флаг                 | Описание                                                          |
|----------------------|-------------------------------------------------------------------|
| `--version`          | Semver-версия (тег в OCI); **обязателен**, без префикса `v`       |
| `--registry`         | Хост реестра образов                                              |
| `--repository-prefix` | Префикс пути репозиториев                                        |
| `--expect-id`        | Требовать совпадение `id` в `template.yaml`                       |

Теги неизменяемы: повторная публикация той же версии будет отклонена. Для новой версии укажите новый semver.

Параметры реестра можно задать в `~/.ddp-template.yaml` или переменными окружения `DDP_TEMPLATE_REGISTRY`, `DDP_TEMPLATE_REPOSITORY_PREFIX`, `DDP_TEMPLATE_REGISTRY_USER`, `DDP_TEMPLATE_REGISTRY_TOKEN`.

После публикации:

1. Убедитесь, что в источнике реестра шаблонов указаны тот же «Реестр» и «Префикс репозиториев».
1. Если заполнены «Идентификаторы репозиториев», добавьте в список `id` нового шаблона.
1. На вкладке «Запуски синхронизации» нажмите «Синхронизировать сейчас» (или дождитесь интервала).
1. Шаблон появится во вкладке «Шаблоны» и в разделе главной «Создать микросервис».

#### `pull`

```bash
ddp-template pull go-service --version 1.1.0 \
  --registry registry.example.org \
  --repository-prefix ddp-templates \
  --output ./packs/go-service-1.1.0
```

| Флаг                 | Описание                                                       |
|----------------------|----------------------------------------------------------------|
| `--version`          | Semver-версия; **обязателен**                                  |
| `--registry`         | Хост реестра образов                                           |
| `--repository-prefix` | Префикс пути репозиториев                                     |
| `--output`           | Каталог распаковки (по умолчанию `./{templateId}-{version}`)   |

#### `render`

```bash
ddp-template render ./my-template --output ./render-out
ddp-template render ./packs/go-service-1.1.0 \
  --values ./values-from-lock.yaml \
  --use-overwrite \
  --output ./render-out
```

| Флаг                 | Описание                                                              |
|----------------------|-----------------------------------------------------------------------|
| `--output`           | Каталог результата; **обязателен**                                    |
| `--values`           | YAML со значениями (по умолчанию `values.yaml` пакета)                |
| `--use-overwrite`    | Рендерить только пути из `update.overwrite` (симуляция selective)     |
| `--upgrade-strategy` | Стратегия для симуляции (по умолчанию из `template.yaml`)             |
| `--paths`            | Список glob через запятую — рендерить только эти пути                 |

## Lock-файл сервиса

В репозитории микросервиса платформа ведёт файл `.ddp/template.lock.yaml`. Это не часть пакета шаблона: файл появляется при создании сервиса из шаблона и обновляется при каждом успешном обновлении.

Пример:

```yaml
templateId: go-service
templateVersion: "1.1.0"
schemaVersion: 1
values:
  slug: payments-api
  name: Payments API
```

| Поле              | Назначение                                                                 |
|-------------------|----------------------------------------------------------------------------|
| `templateId`      | Идентификатор шаблона (`id` из `template.yaml`)                            |
| `templateVersion` | Версия шаблона, применённая к репозиторию                                  |
| `schemaVersion`   | Версия формата файла (сейчас `1`)                                          |
| `values`          | Значения, с которыми рендерился пакет                                      |

Зачем он нужен:

- при **обновлении** платформа читает lock: какой шаблон обновлять и с какими `values` снова рендерить файлы;
- после merge MR сверка версии читает lock из ветки по умолчанию и при необходимости обновляет параметр «Версия шаблона» у сущности в каталоге;
- без lock обновление из шаблона невозможно.

Не удаляйте и не переименовывайте файл вручную. Менять `templateVersion` руками обычно не нужно: его обновляет процесс обновления.

## Обновление сервиса до новой версии шаблона

Когда в OCI появляется новая версия шаблона и реестр её синхронизирует, у микросервисов, созданных из этого шаблона, на главной в разделе «Микросервисы» показывается, что доступна новая версия.

### Как применяется обновление

1. Платформа загружает целевую версию пакета из OCI.
1. Читает `.ddp/template.lock.yaml` в репозитории сервиса.
1. Рендерит пакет с `values` из lock (при необходимости с дополнением из процесса).
1. Вносит изменения в файлы по [стратегии обновления](#стратегии-обновления) из `template.yaml` (или по переопределению у сущности / в параметрах процесса).
1. Обновляет в lock поле `templateVersion` (и при необходимости `values`).
1. Создаёт feature-ветку (префикс из настройки «Префикс ветки обновления» + версия) и код-ревью (Merge Request) в GitLab. Заголовок ревью — `Upgrade <идентификатор шаблона> to <версия>`, например `Upgrade go-service to 1.2.3` (и при ручном, и при автоматическом запуске).
1. После принятия MR сверка версии подтягивает `templateVersion` из lock в параметр сущности «Версия шаблона».

Пока MR не принят, в каталоге может оставаться прежняя «Версия шаблона». После merge при включённой синхронизации фоновая сверка читает lock из ветки по умолчанию и поднимает версию в каталоге.

### Запуск вручную

1. Откройте «Главная» → «Микросервисы».
1. У сервиса с доступным обновлением нажмите «Обновить».
1. При необходимости выберите процесс и подтвердите запуск.

Запускается процесс «Обновление микросервиса из шаблона» (из набора данных «Реестр шаблонов микросервисов»).

### Автоматический запуск

У сущности микросервиса в каталоге задайте параметр «Политика обновления шаблона»:

| Значение в интерфейсе     | Поведение                                                                                                                   |
|---------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| «Вручную»                 | Обновление только по кнопке «Обновить» на главной                                                                           |
| «Ревью автоматически»     | После синхронизации, когда сменилась рекомендуемая («последняя») версия шаблона, платформа сама ставит обновление в очередь |

Для автоматики укажите «Пользователь автоматизации» в настройках реестра шаблонов. Пустое значение — автоматизация выключена. Число постановок за одну синхронизацию ограничивает «Лимит очереди обновлений».

### Параметры сущности в каталоге

У микросервиса, созданного из шаблона, хранятся в том числе:

| Название в интерфейсе              | Назначение                                              |
|------------------------------------|---------------------------------------------------------|
| «Идентификатор шаблона»            | Какой шаблон привязан                                   |
| «Версия шаблона»                   | Версия в каталоге (после merge подтягивается из lock)   |
| «Источник шаблона»                 | Название источника из настроек реестра                  |
| «Политика обновления шаблона»      | «Вручную» или «Ревью автоматически»                     |
| «Стратегия обновления шаблона»     | Необязательное переопределение стратегии из пакета      |

## Источники

На вкладке «Источники» настраиваются реестры образов, из которых платформа читает шаблоны.

| Название                      | Описание                                                                          | Обязательность |
|-------------------------------|-----------------------------------------------------------------------------------|----------------|
| «Название»                    | Уникальное название источника                                                     | **да**         |
| «Реестр»                      | Хост реестра образов, например `registry.vendor.example`                          | **да**         |
| «Префикс репозиториев»        | Префикс пути внутри реестра, например `ddp-templates`                             | нет            |
| «Идентификаторы репозиториев» | Список разрешённых идентификаторов шаблонов; пусто — использовать каталог реестра | нет            |
| «Имя пользователя»            | Учётная запись для доступа к реестру                                              | нет            |
| «Пароль»                      | Пароль; оставьте маску без изменений, чтобы сохранить текущий пароль              | нет            |
| «Пропускать проверку TLS»     | Только для лабораторных сред и самоподписанных сертификатов                       | нет            |

Удаление или переименование источника делает его шаблоны недоступными; записи в каталоге не удаляются.

## Настройки

### Синхронизация

| Название                                  | Описание                                                                                                 |
|-------------------------------------------|----------------------------------------------------------------------------------------------------------|
| «Включить синхронизацию»                  | Включает периодическую синхронизацию и фоновую сверку версии шаблона сервиса с lock-файлом в репозитории |
| «Интервал синхронизации»                  | Длительность в формате Go, например `15m`                                                                |
| «Максимальный размер шаблона (килобайты)» | Шаблон больше лимита отклоняется при синхронизации                                                       |

### Значения по умолчанию для создаваемых сервисов

| Название                   | Описание                                                                                                                                                         |
|----------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| «Ветка по умолчанию»       | Ветка по умолчанию для создаваемых сервисов                                                                                                                      |
| «Префикс ветки обновления» | Префикс feature-ветки обновления шаблона; к нему добавляется версия. Смена префикса не учитывает уже открытые MR со старым префиксом                              |

### Сверка версии и автоматизация

| Название                         | Описание                                                                                       |
|----------------------------------|------------------------------------------------------------------------------------------------|
| «Интервал сверки версии шаблона» | Длительность в формате Go, например `5m`                                                       |
| «Лимит очереди обновлений»       | Максимум постановок обновления в очередь за одну синхронизацию                                 |
| «Пользователь автоматизации»     | Пользователь для автоматизации обновлений после синхронизации; пусто — автоматизация выключена |

Политика обновления шаблона у микросервиса задаётся в каталоге. Подробнее — в разделе [«Обновление сервиса до новой версии шаблона»](#обновление-сервиса-до-новой-версии-шаблона).

## Шаблоны

Вкладка «Шаблоны» показывает шаблоны реестра (последние версии). Раскройте строку, чтобы увидеть все версии шаблона. Фильтр «Источник удалён из настроек» показывает только записи источников, которых больше нет в настройках; теги, удалённые из OCI, получают статус «отозвана».

Доступные действия:

- «Отозвать версию» — версия скрывается из галереи и автоматизации; тег в реестре образов не удаляется. В диалоге можно указать «Причина».
- «Вернуть версию» — версия снова доступна.
- «Удалить» — удаление версии из платформы; при следующей синхронизации она может появиться снова, если тег ещё есть в реестре.
- «Удалить осиротевшие» — безвозвратное удаление версий, чей источник образов больше не настроен.

Статусы версии: «доступна», «отозвана», «некорректна», «недоступна». Метка «последняя» — текущая рекомендуемая версия среди доступных для шаблона (отозванные не учитываются).

## Запуски синхронизации

На вкладке «Запуски синхронизации» отображаются последние запуски и кнопка «Синхронизировать сейчас».

Счётчики показывают число операций, а не размер каталога. «Конфликт» — одна и та же версия шаблона есть в нескольких источниках (остаётся первая).

## Использование на главной

- «Создать микросервис» — галерея шаблонов; выберите версию, систему и при необходимости процесс. Затем в одном окне задайте идентификатор и название микросервиса, описание репозитория и параметры из `values.yaml` шаблона. Параметры VCS (например «Группа GitLab») задаются в форме запуска процесса. Значения из `values.yaml` подтягиваются при синхронизации.
- «Микросервисы» — кнопка «Обновить», если доступна новая версия шаблона. Подробнее — в разделе [«Обновление сервиса до новой версии шаблона»](#обновление-сервиса-до-новой-версии-шаблона).

## Типичные сбои

| Симптом                                          | Что проверить                                                                                                                                  |
|--------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Обновление не запускается или падает сразу       | В репозитории сервиса есть `.ddp/template.lock.yaml`, `templateId` совпадает с шаблоном                                                        |
| Процесс обновления завершился с ошибкой merge    | Стратегия `merge`: конфликт в путях из `overwrite`; разрешите конфликт вручную или смените стратегию                                           |
| Новая версия не появляется в реестре             | Тег в OCI — semver без `v`; если заполнены «Идентификаторы репозиториев», в списке есть `id` шаблона; синхронизация выполнена                   |
| Версия есть в OCI, в платформе статус «отозвана» | Тег удалили из реестра образов или версию отозвали вручную; верните тег или нажмите «Вернуть версию»                                           |
| «Ревью автоматически» не создаёт MR              | Задан «Пользователь автоматизации»; у сущности политика «Ревью автоматически»; после синхронизации сменилась рекомендуемая («последняя») версия |
| Кнопка «Обновить» недоступна или нет процесса    | Применён набор данных «Реестр шаблонов микросервисов»; у сущности заполнены «Идентификатор шаблона» и «Версия шаблона»                          |

## Права доступа

- `read:template-registry` — просмотр настроек и каталога шаблонов.
- `update:template-registry` — изменение источников и настроек, отзыв и удаление версий.
- `sync:template-registry` — запуск синхронизации.

Подробнее — в разделе [«Ролевая модель»](../security/rbac/).
