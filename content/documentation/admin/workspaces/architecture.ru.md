Deckhouse Development Portal (DDP) разделяет управление рабочим пространством, создание инфраструктуры и выполнение заданий. Это позволяет запускать служебные Jobs в одном Kubernetes-кластере, а рабочее пространство размещать в другом.

## Компоненты

Компоненты выполняют следующие функции:

| Компонент | Назначение |
| --- | --- |
| DDP backend | Принимает операции, проверяет владельца, разрешения и квоты; выдаёт временный доступ и наблюдает готовность |
| Хранилище DDP | Сохраняет файлы шаблона, версии, параметры, планы, состояние OpenTofu и историю |
| Job подготовки | Проверяет OpenTofu-пакет и провайдеры, добавляет файл блокировки зависимостей |
| Job исполнения | Выполняет планирование, применение изменений и удаление инфраструктуры |
| Провайдер DDP | Передаёт OpenTofu контекст операции и описывает параметры, среду, скрипты и политики хранения |
| Провайдер Kubernetes | Создаёт и изменяет Kubernetes-объекты через контролируемый доступ DDP |
| Исполнитель среды | Подготавливает файлы, выполняет скрипты и обслуживает задания через OpenCode |
| code-server | Предоставляет редактор и терминал в браузере |
| Постоянный том | Сохраняет репозиторий, инструменты, настройки IDE и состояние OpenCode |

## Служебное и целевое подключения

«Настройки подключения» задают внешний сервис Kubernetes и неймспейс, где DDP создаёт служебные Jobs. Сервис определяет адрес Kubernetes API и реквизиты для управления этими Jobs.

Шаблон определяет другое подключение: внешний сервис и неймспейс для Pod, PVC и остальных объектов рабочего пространства. Встроенная основа получает эти значения из формы «Создать шаблон». После создания администратор может изменить переменные `kubernetes_service_uuid` и `namespace` в файлах шаблона.

Например, служебные Jobs выполняются в кластере A, а Pod и PVC создаются в кластере B:

| Уровень | Подключение | Неймспейс | Что размещается |
| --- | --- | --- | --- |
| «Настройки подключения» | Внешний сервис кластера A | `ddp-jobs` | Jobs подготовки и исполнения |
| Шаблон | Внешний сервис кластера B | `team-workspaces` | Pod, PVC и вспомогательные объекты |

Job обращается к DDP, а DDP выполняет разрешённые запросы к целевому Kubernetes API. Job не подключается к кластеру B через персональный `kubeconfig`. Backend должен иметь сетевой доступ к обоим Kubernetes API; Jobs и рабочее пространство должны иметь доступ к HTTPS-адресу backend.

Сохранённое пространство закрепляет целевое подключение и неймспейс. Изменение активной версии шаблона не переносит его в другой кластер.

## Учётные данные

Подключение служебных Jobs использует системного пользователя, заданного во внешнем сервисе, для подстановки ссылок на учётные данные. Если сервис содержит готовый заголовок авторизации, отдельный пользователь для подстановки не требуется.

Для целевого подключения шаблон задаёт `credentials_mode`:

| Значение | Чьи учётные данные разрешает DDP |
| --- | --- |
| `owner` | Владельца рабочего пространства |
| `fixed_user` | Пользователя из `credential_user_uuid` |

Готовый заголовок авторизации во внешнем сервисе остаётся общим для этого сервиса. Режим `owner` влияет на подстановку пользовательских реквизитов; он не преобразует общий токен в персональный.

Реквизиты GitLab разрешаются для владельца рабочего пространства. Реквизиты AI-провайдера используются backend при обращении к модели. OpenCode и code-server не получают административный токен DDP или токен Kubernetes.

Значения реквизитов разрешаются заново при обращениях к внешнему сервису. Можно ротировать токен при сохранении идентичности подключения. Смена адреса сервиса, режима TLS или пользователя реквизитов может нарушить закреплённое подключение; такую смену выполняйте после завершения зависимых операций и удаления зависимых пространств.

## Состояние и постоянные данные

DDP хранит состояние разных уровней раздельно:

| Уровень | Содержимое | Где хранится |
| --- | --- | --- |
| Шаблон | Исходные файлы, ревизия, опубликованные версии, декларации формы | Хранилище DDP |
| Инфраструктура | State OpenTofu, сохранённый план, принадлежность объектов | Зашифрованное хранилище DDP |
| Среда | Checkout, локальные коммиты, SDK, IDE, состояние OpenCode | PVC |
| Выполнение | Операции, задания, события, ответы и известный расход модели | Хранилище DDP |
| Временный доступ | Токены операций, задания, IDE и управления | Ограниченные по сроку реквизиты и временные директории |

PVC сохраняется при остановке. Восстановление подключает прежний том и прежнюю сессию OpenCode, выдавая новые временные реквизиты. Отсутствие ожидаемого тома или несовпадение его идентичности приводит к ошибке восстановления.

Удаление пространства уничтожает принадлежащую ему инфраструктуру и постоянные данные. История чата, заданий и операций остаётся в DDP.

## Сериализация операций

DDP допускает одну изменяющую инфраструктуру операцию для рабочего пространства. Сохранённый план связан с версией шаблона, параметрами, поколением среды и текущим состоянием OpenTofu. Перед применением DDP проверяет, что эти значения остались актуальными.

Потеря связи с исполнителем не позволяет сразу выдать второму исполнителю доступ к записи. DDP сначала отзывает прежнее разрешение и подтверждает завершение процессов и записи в том. Поэтому при неопределённом состоянии операция может оставаться заблокированной, даже если под уже исчез из обычного списка.

Проверка завершения использует фактические UID Pod, PVC, PV, состояние контейнеров, Node, Lease узла и подключение тома. Права чтения этих объектов входят [в требования к Kubernetes-доступу](permissions/#доступ-к-kubernetes).

## IDE и чат

IDE публикуется через backend по пути `/workspace-ide/` на HTTPS-домене установки. Доступ проверяет владельца, состояние, срок работы, поколение и фактический UID пода. Билет открывает сессию IDE конкретного рабочего пространства. При остановке и смене поколения прежний доступ отзывается.

Содержимое IDE выполняется в общем браузерном origin DDP. Редактор, расширения и предпросмотр кода входят в доверенный браузерный контекст пользователя. Прокси удаляет заголовки авторизации и cookie приложения перед передачей запроса в code-server.

Рабочее пространство можно прикрепить к одному чату. Ассистент чата делегирует работу через `workspace_run_task` и получает результат через `workspace_get_task`. OpenCode выполняет задание в сохранённой сессии и получает ограниченный набор инструментов MCP владельца. Отсоединение от чата сохраняет среду и данные.
