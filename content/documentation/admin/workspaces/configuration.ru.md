Для запуска рабочих пространств настройте установку Deckhouse Development Portal (DDP), подключение служебных Jobs и целевое подключение шаблона. Backend должен обращаться к Kubernetes API и GitLab, а служебные Jobs и среда должны обращаться к HTTPS-адресу backend.

## Первый запуск

Первое рабочее пространство создаётся после настройки установки и публикации шаблона:

1. Настройте параметры `workspaces` модуля `development-platform`.
1. Создайте внешний сервис Kubernetes с адресом API и заголовками авторизации.
1. Откройте «AI» → «Шаблоны рабочих пространств» → «Настройки подключения».
1. Выберите внешний сервис для служебных Jobs и укажите существующий неймспейс.
1. Сохраните настройки.
1. Создайте [шаблон](templates/) с целевым Kubernetes-сервисом и неймспейсом, опубликуйте и активируйте его.
1. Выдайте [права пользователям](permissions/) и подготовьте GitLab- и AI-подключения.

Сохранение «Настроек подключения» проверяет формат и доступность реквизитов в DDP. Обращения к Kubernetes при сохранении не выполняются; права кластера проверяются во время операций.

## Параметры установки

Модуль `development-platform` поставляет образы подготовки, среды и IDE вместе со своим релизом. Администратор задаёт адрес backend, ресурсы Jobs и ключ подписи служебных токенов.

Параметры находятся в `settings.workspaces` ModuleConfig. Для включения модуля используйте [настройки модуля](/modules/development-platform/configuration.html#enable). Пример значения `workspaces`:

```yaml
workspaces:
  secretKey: "<WORKSPACE_SIGNING_KEY>"
  backendUrl: "https://ddp.example.com"
  jobResources:
    cpuMillicores: 500
    memoryBytes: 1073741824
    temporaryBytes: 134217728
```

Замените `<WORKSPACE_SIGNING_KEY>` постоянным секретным значением от `32` до `4096` печатных ASCII-символов. Замените `ddp.example.com` доменом backend. Числа в примере выделяют каждому служебному Job `500m` CPU, `1 GiB` памяти и `128 MiB` временного хранилища.

Параметры имеют следующие значения:

| Параметр | Назначение | Условие |
| --- | --- | --- |
| `secretKey` | Подпись служебных токенов рабочих пространств | Обязателен при заданном `workspaces`; одинаковый для backend и workers |
| `backendUrl` | HTTPS-origin backend для Jobs, среды и IDE | Задаётся вместе с `jobResources` |
| `jobResources.cpuMillicores` | Запрос и лимит CPU Job в милликор | Положительное целое |
| `jobResources.memoryBytes` | Запрос и лимит памяти Job в байтах | Положительное целое; включает рабочую директорию в памяти |
| `jobResources.temporaryBytes` | Вместимость временной рабочей директории Job в байтах | Положительное целое |

URL задаёт origin, например `https://ddp.example.com`; путь IDE backend добавляет сам. DNS-имя должно разрешаться из служебного неймспейса и целевой среды. TLS-сертификат должен соответствовать имени и проверяться клиентами.

Параметры CPU, памяти и диска самого рабочего пространства задаются в шаблоне, независимо от ресурсов служебного Job.

## Служебный ключ

`workspaces.secretKey` подписывает временный доступ к операциям. Ключ отличается от `security.secretKey`, используемого для шифрования сохранённых данных. Сохраните оба ключа в управляемой конфигурации установки.

Для получения случайного значения можно использовать:

```shell
openssl rand -hex 32
```

Сохраните результат в `secretKey`. Jobs получают токен своей операции; ключ подписи остаётся у backend и workers. Смена ключа делает ранее выданные служебные токены недействительными.

## Подключение служебных Jobs

«Настройки подключения» определяют кластер и неймспейс Jobs подготовки и OpenTofu-исполнения. Внешний сервис хранит URL Kubernetes API, TLS-настройки и заголовки авторизации.

Если заголовки используют ссылки на учётные данные DDP, во внешнем сервисе задайте системного пользователя, для которого эти ссылки разрешаются. Предоставьте этому пользователю права [управления Jobs](permissions/#доступ-к-kubernetes).

Изменения общих настроек применяются к новым операциям. Принятая операция сохраняет выбранное подключение и неймспейс. Ротация значения реквизита сохраняет подключение, а смена его идентичности может заблокировать продолжение операции.

До сохранения настройки DDP запускается, но публикация и операции, которым требуется служебный Job, сообщают об отсутствии подключения.

## Целевое подключение

Форма создания шаблона явно запрашивает внешний сервис Kubernetes и namespace. DDP сохраняет значения в переменных `kubernetes_service_uuid` и `namespace` редактируемого черновика. Форма не проверяет наличие неймспейса в кластере.

Служебные настройки не выбирают целевые реквизиты автоматически. Целевой сервис может относиться к другому кластеру. Выбор владельца или фиксированного пользователя задаётся [в декларации шаблона](opentofu-provider/#декларация-шаблона).

Для режима `existing` подготовьте существующий неймспейс и укажите ровно одно значение в `allowed_namespaces`. При создании рабочего пространства пользователь увидит закреплённый сервис и неймспейс. В режиме `per_workspace` DDP выбирает неймспейс по идентификатору рабочего пространства; правила создания приведены [в примере](examples/#отдельный-неймспейс).

## Backend вне модуля

При запуске backend вне установленного модуля образы задаются явно в конфигурации backend. К настройкам `workspaces` добавляются ссылки:

```yaml
workspaces:
  provisioner:
    image: "<PROVISIONER_IMAGE>@sha256:<PROVISIONER_SHA256>"
  runtime:
    image: "<RUNTIME_IMAGE>@sha256:<RUNTIME_SHA256>"
  ide:
    image: "<IDE_IMAGE>@sha256:<IDE_SHA256>"
```

Это фрагмент конфигурации backend, дополнение к `secretKey`, `backendUrl` и `jobResources`. Замените имена образов адресами хранилища, а SHA-256 — `64` строчными шестнадцатеричными символами. Все процессы используют одинаковую конфигурацию. Во внешней конфигурации ModuleConfig эти поля не задаются: модуль получает образы из релиза.

При локальном запуске `WORKSPACES_SECRET_KEY` или `--workspaces-secret-key` переопределяют `workspaces.secretKey`. HTTPS-адрес должен оставаться доступным из Kubernetes, даже если интерфейс DDP открывается локально.

## Лимиты и квоты

Откройте «AI» → «Шаблоны рабочих пространств» → «Лимиты и квоты». Политика действует для всех шаблонов и пользователей установки. Исходные значения:

| Поле | Исходное значение |
| --- | --- |
| Запущенных рабочих пространств на пользователя | `2` |
| Сохранённых рабочих пространств на пользователя | `4` |
| Запущенных рабочих пространств всего | `8` |
| Сохранённых рабочих пространств всего | `16` |
| Управляемых ресурсов Kubernetes на рабочее пространство | `32` |
| Файлов в пакете | `256` |
| Размер одного файла | `1 MiB` |
| Суммарный размер содержимого файлов пакета | `16 MiB` |
| Размер журнала операции | `1 MiB` |
| Время подготовки | `300` секунд |
| Время выполнения скрипта | `300` секунд |

Работающее пространство занимает активную и сохранённую квоты. Остановленное занимает сохранённую квоту. При ошибке очистки DDP удерживает соответствующие резервации до подтверждённого удаления объектов. Уменьшение квоты не удаляет существующие пространства.

Допустимые значения и зависимости полей описаны [в ограничениях](troubleshooting/#ограничения).
