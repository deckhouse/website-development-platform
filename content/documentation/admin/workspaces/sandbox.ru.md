Рабочее пространство можно запускать в изолированной среде Kata Containers или gVisor. Для этого укажите RuntimeClass в OpenTofu-шаблоне рабочего пространства. Менять код DDP и пересобирать его образы не требуется.

RuntimeClass применяется ко всему поду: агенту OpenCode, IDE, веб-терминалу, шлюзу `gate` и контейнеру `bootstrap`. В штатном шаблоне они используют общую сеть и постоянный том.

## Подготовка кластера

В целевом кластере Kubernetes должны быть настроены Kata Containers или gVisor и соответствующий RuntimeClass. Установка среды выполнения зависит от конфигурации кластера: [инструкция Kata Containers](https://github.com/kata-containers/kata-containers/tree/main/tools/packaging/kata-deploy), [инструкция gVisor](https://gvisor.dev/docs/user_guide/quick_start/kubernetes/).

Проверьте доступные классы с правами администратора целевого кластера:

```shell
d8 k --context=workspace-cluster get runtimeclass
```

Замените `workspace-cluster` на контекст целевого кластера. Выберите название из `metadata.name` RuntimeClass, например `kata-qemu` или `gvisor`. Название класса и его `handler` могут различаться; в шаблоне указывается название класса.

Если среда выполнения доступна только на части узлов, настройте `scheduling.nodeSelector` и при необходимости `scheduling.tolerations` в RuntimeClass. Без этих ограничений Kubernetes считает, что класс поддерживается всеми узлами. Дополнительные затраты CPU и памяти задаются в `overhead`. Порядок настройки описан [в документации RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/).

Подготовьте также [подключение Kubernetes, сеть и постоянный том](overview/). Проверьте, что выбранная среда выполнения поддерживает используемое хранилище и сетевые подключения рабочего пространства.

## Указание среды выполнения в шаблоне

Для запуска на определённом RuntimeClass измените черновик [шаблона рабочего пространства](templates/):

1. Откройте «AI» → «Рабочие пространства» → «Шаблоны рабочих пространств» и выберите шаблон.
1. На вкладке «Файлы» откройте `main.tf`.
1. Найдите `resource "kubernetes_stateful_set_v1" "runtime"` и добавьте в его блок `spec` → `template` → `spec` поле:

   ```hcl
   runtime_class_name = "kata-qemu"
   ```

1. Замените `kata-qemu` на название выбранного класса. Например, для класса gVisor с названием `gvisor` укажите `runtime_class_name = "gvisor"`.
1. Сохраните черновик и [проверьте запуск](#проверка-запуска).
1. После проверки опубликуйте и активируйте новую версию шаблона.

Поле находится на уровне пода, рядом с `automount_service_account_token` и `security_context`. Добавлять его в отдельный контейнер или в `ddp_runtime` не требуется. Штатный провайдер Kubernetes поддерживает `runtime_class_name`.

Для существующего рабочего пространства остановите его, выполните [обновление версии шаблона](../../user/workspaces/#обновление-шаблона) и запустите снова. Публикация версии сама по себе существующие пространства не обновляет.

## Автоматический выбор доступного класса

Если один шаблон должен выбирать Kata или gVisor по наличию RuntimeClass, запросите список классов из целевого кластера. Учётной записи [подключения Kubernetes шаблона](overview/#выбор-учётных-данных) потребуется право `list` на `runtimeclasses` в API-группе `node.k8s.io` на уровне кластера. При отсутствии права запрос завершится ошибкой доступа.

Добавьте в `main.tf` запрос и блок локальных значений:

```hcl
data "kubernetes_resources" "sandbox_runtime_classes" {
  api_version = "node.k8s.io/v1"
  kind        = "RuntimeClass"
}

locals {
  sandbox_runtime_priority = ["kata-qemu", "kata", "gvisor"]
  available_runtime_classes = [
    for runtime_class in data.kubernetes_resources.sandbox_runtime_classes.objects :
    runtime_class.metadata.name
  ]
  matching_sandbox_classes = [
    for name in local.sandbox_runtime_priority : name
    if contains(local.available_runtime_classes, name)
  ]
  sandbox_runtime_class = length(local.matching_sandbox_classes) > 0 ? local.matching_sandbox_classes[0] : null
}
```

В `sandbox_runtime_priority` укажите названия классов вашей установки в порядке выбора. Пример выбирает первый существующий класс: сначала `kata-qemu`, затем `kata`, затем `gvisor`. Наличие RuntimeClass проверяет регистрацию класса, но не работоспособность его обработчика на узлах.

В блоке `spec` → `template` → `spec` StatefulSet используйте выбранное значение вместо фиксированной строки:

```hcl
runtime_class_name = local.sandbox_runtime_class
```

Чтобы отсутствие подходящего класса останавливало применение шаблона, добавьте проверку в существующий блок `lifecycle` этого StatefulSet. Сохраните его настройку `ignore_changes`:

```hcl
lifecycle {
  ignore_changes = [spec[0].replicas]

  precondition {
    condition     = local.sandbox_runtime_class != null
    error_message = "No configured sandbox RuntimeClass is available in the target cluster."
  }
}
```

При пустом списке совпадений операция завершится указанной ошибкой. Этот пример требует sandbox и не запускает рабочее пространство на среде выполнения кластера по умолчанию.

Выбор выполняется при создании или обновлении рабочего пространства, когда применяется OpenTofu-шаблон. Обычные остановка и запуск меняют число реплик StatefulSet и используют уже сохранённый класс. Для повторного выбора выполните обновление рабочего пространства.

## Проверка запуска

Создайте новое рабочее пространство из черновика, доступного редактору шаблона. Затем проверьте результат:

1. Дождитесь успешной операции создания и статуса «Работает».
1. Проверьте класс фактически созданного пода:

   ```shell
   d8 k --context=workspace-cluster -n workspace-team get pod ddp-ws-0a26ad26-0 -o jsonpath='{.spec.runtimeClassName}{"\n"}'
   ```

   Замените контекст, неймспейс и название пода на значения рабочего пространства. Название пода доступно в его диагностике. Команда должна вывести выбранный класс, например `kata-qemu` или `gvisor`.

1. Проверьте, что под готов, а в его событиях нет ошибок запуска среды выполнения. Значение `runtimeClassName` само по себе показывает только запрошенный класс.
1. Откройте IDE и веб-терминал, выполните задание агента в чате и проверьте публикацию HTTP-приложения, если она используется.
1. Создайте файл в рабочей директории, остановите и снова запустите рабочее пространство. Проверьте, что файл сохранился и класс пода остался выбранным.

Работу приложений и инструментов проверяйте на выбранной среде выполнения: поддержка системных вызовов, устройств и операций с файлами зависит от Kata или gVisor и их конфигурации.

## Устранение ошибок

При ошибке откройте [диагностику рабочего пространства](../../user/workspaces/#диагностика), логи операции и события пода:

| Симптом | Что проверить |
| --- | --- |
| Ошибка доступа при чтении RuntimeClass | Право `list` у учётной записи целевого Kubernetes-подключения; применяется только к автоматическому выбору |
| `No configured sandbox RuntimeClass is available in the target cluster.` | Названия в `sandbox_runtime_priority` и наличие соответствующих RuntimeClass |
| Под не создаётся или не запускается после выбора класса | Существование RuntimeClass, настройку его `handler` на узлах и события StatefulSet и пода |
| Под остаётся в состоянии Pending | Ограничения размещения RuntimeClass, taints узлов, доступные CPU и память с учётом `overhead`, подключение постоянного тома |
| Контейнер запускается, но инструмент завершается ошибкой | Логи контейнера и совместимость инструмента с выбранной средой выполнения |

## Границы настройки

Шаблон задаёт среду выполнения пода рабочего пространства. Job операции OpenTofu запускается отдельно; его среда выполнения определяется настройками кластера, в котором выполняются Jobs операций.

RuntimeClass выбирает среду выполнения контейнеров. Для ограничения сетевых соединений настройте NetworkPolicy отдельно; доступ к объектам портала по-прежнему регулируется [ролевой моделью DDP](../security/rbac/#рабочие-пространства-и-шаблоны).
