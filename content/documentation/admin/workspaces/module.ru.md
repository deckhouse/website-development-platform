Новый шаблон Deckhouse Development Portal (DDP) содержит локальный модуль `./modules/workspace`. Он создаёт постоянный PVC, временный Pod основной среды, приватный источник данных запуска и среды для проверки и подготовки файлов. Исходники модуля входят в редактируемый пакет каждого шаблона.

## Состав объектов

Модуль связывает имена с постоянным суффиксом рабочего пространства и поколением запуска:

| Объект | Условие создания | Хранение |
| --- | --- | --- |
| PVC `data` | Существует независимо от `start_count` | Сохраняется при Stop и Restore; класс `protected` |
| Secret `source` | `start_count = 1` | Источник временного доступа, класс `ephemeral` |
| Pod `runtime` | `start_count = 1` | Основная среда, класс `ephemeral` |
| Pod `inspection` | `inspection_count = 1` | Чтение постоянных файлов при обновлении |
| Pod `preparation` | `preparation_count = 1` | Применение согласованных файлов и скриптов к остановленной среде |

PVC имеет имя `ddp-data-<SUFFIX>`. Основной Pod включает поколение: `ddp-g<GENERATION>-<SUFFIX>`. Имена разных рабочих пространств не конфликтуют в общем неймспейсе.

Модуль объявляет единственный `ddp_runtime` и политики соответствующих объектов. При остановке OpenTofu удаляет временные объекты, сохраняя PVC.

## Подготовка и запуск

Init-контейнер получения материалов обращается к DDP с временным разрешением и фактическим UID Pod. Он записывает приватные входы запуска во временные тома. Следующий init-контейнер подготавливает репозиторий и сохраняемую структуру данных.

Контейнер `runtime` выполняет принятые действия с файлами и скриптами, затем запускает OpenCode. Контейнер IDE запускает code-server с тем же checkout и постоянными пользовательскими директориями. Готовность DDP означает завершение необходимой подготовки и доступность среды, а не только наличие Pod со статусом `Running`.

Среда не монтирует токен ServiceAccount автоматически. Контейнеры запускаются без root, с отключённым повышением привилегий, без Linux capabilities и с корневой файловой системой только для чтения. Записываемые файлы находятся в PVC и явно выделенных временных томах.

## Параметры модуля

Вызов `module "workspace"` в `main.tf` передаёт параметры локального модуля. Образы `runtime_image` и `ide_image` при создании шаблона получает DDP из конфигурации установки. Остальные исходные значения доступны для редактирования.

Полный список входов:

| Параметр | Тип | Исходное значение | Назначение |
| --- | --- | --- | --- |
| `runtime_image` | `string` | Digest образа релиза | Исполнитель и вспомогательные программы подготовки |
| `ide_image` | `string` | Digest образа релиза | code-server и управляющий процесс IDE |
| `runtime_profile` | Объект | Профиль версии `1` | Пути, OpenCode, IDE и ограничения |
| `persistent_directory` | `string` | `/workspace` | Точка монтирования постоянного тома |
| `attempt_directory` | `string` | `/run/attempt` | Основа временной директории поколения |
| `control_port` | `number` | `14097` | Порт управления средой |
| `ide_port` | `number` | `18080` | Порт IDE |
| `storage_class` | `string` или `null` | `null` | StorageClass; `null` выбирает класс по умолчанию в кластере |
| `storage_size` | `string` | `10Gi` | Запрошенный объём PVC |
| `access_modes` | `list(string)` | `["ReadWriteOnce"]` | Режим доступа к тому |
| `service_account` | `string` | `default` | ServiceAccount пода |
| `uid` | `number` | `10000` | UID процессов |
| `gid` | `number` | `10000` | GID процессов и группы доступа к тому |
| `runtime_resources` | Объект `cpu/memory` | `500m/1Gi` | Запросы и лимиты контейнера исполнителя |
| `ide_resources` | Объект `cpu/memory` | `500m/1Gi` | Запросы и лимиты IDE |
| `bootstrap_resources` | Объект `cpu/memory` | `500m/1Gi` | Запросы и лимиты подготовки |
| `temporary_size` | `string` | `128Mi` | Лимит каждого временного тома в памяти |
| `termination_grace_seconds` | `number` | `10` | Время завершения Pod |
| `node_selector` | `map(string)` | `{}` | Выбор узлов |
| `files` | Список объектов | `[]` | Содержимое для доставки в проект |

`runtime_resources`, `ide_resources` и `bootstrap_resources` содержат строковые поля `cpu` и `memory` в формате Kubernetes quantity. У встроенного модуля значения одновременно используются как requests и limits. Суммарная потребность основного Pod включает исполнитель и IDE; init-контейнеры учитываются Kubernetes по правилам планирования Pod.

Конфигурация постоянного хранилища должна соответствовать StorageClass целевого кластера. Изменение имени, неймспейса или замена защищённого PVC блокируются при обычном обновлении. Сохранение на PVC не заменяет резервное копирование хранилища.

Схема профиля и файлов приведена [в профиле среды](runtime-profile/).

## Редактирование инфраструктуры

Исходный модуль можно менять в редакторе DDP. Сохраняйте обязательную декларацию `ddp_runtime`, привязку к workspace/generation, постоянный том и разделение временных и постоянных директорий.

Дополнительные Kubernetes-объекты должны соответствовать поддерживаемым профилям доступа DDP. Поддерживаются прямые объекты:

- Pod;
- PersistentVolumeClaim;
- Secret типа `Opaque`;
- ConfigMap;
- ServiceAccount;
- Namespace;
- ResourceQuota;
- LimitRange;
- NetworkPolicy.

ResourceQuota и LimitRange допускаются в собственном неймспейсе рабочего пространства. Запросы с неподдерживаемым видом объекта отклоняются брокером. Подключение Kubernetes с широкими правами само по себе не расширяет поддерживаемые профили.

Объекты должны иметь различимые имена, принадлежность рабочему пространству и допустимые ссылки на тома и реквизиты. Для постоянных объектов используйте `suffix`, для объектов попытки запуска — также `generation`. Существующий общий неймспейс не объявляйте управляемым Namespace.
