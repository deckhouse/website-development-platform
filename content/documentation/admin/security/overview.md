Deckhouse Development Portal (DDP, portal) provides a set of built-in security mechanisms for access control, credential protection, and auditing of user actions in the portal.

## Authentication

DDP authenticates users through the external Dex service deployed as part of Deckhouse Platform.

Dex integrates with external authentication providers (Keycloak, LDAP, and others) through the standard OIDC and LDAP protocols.
DDP Backend uses signing keys obtained from Dex to verify JWT tokens and authenticate API requests.
Authentication is configured on the Deckhouse Platform side; no additional configuration is required in DDP.

## Role model (RBAC)

DDP implements a role-based access model that separates user permissions and controls the operations performed in the portal.

The model supports a role hierarchy and permission checks at the level of the super administrator, global roles, resource roles, and entity roles.
For details, see [Role model](../rbac/).

## Impersonation

DDP lets a user with the `impersonate:users` permission temporarily work in the interface on behalf of another user to check access permissions and troubleshoot problems.
The session is time-limited; operations with the target user's credentials and secrets are unavailable in this mode.

For details, see [Impersonation](../impersonation/).

## Credentials

DDP provides centralized and secure storage of the credentials used to integrate with external systems and services.
Credentials are stored and processed by DDP Backend using a PostgreSQL database.

Before being saved to the database, credentials are encrypted with the AES-GCM algorithm.
DDP Backend decrypts them only when they are used in actions, datasources, or widgets.
For details, see [Credentials](../credentials/).

## Encryption key rotation

When you change the encryption key (the `security.secretKey` module parameter), DDP lets you re-encrypt all related data from the web interface without losing user credentials, Vault secrets, and other encrypted values.
The operation is available to users with the `rotate:encryption-key` permission.
For details, see [Encryption key rotation](../encryption-key-rotation/).

## Trusted certificates

DDP lets you add root and intermediate certificates (CA) or server certificates to the store.
They are used for TLS verification in outgoing HTTPS requests to external services (in actions, widgets, datasources, and other components).

Trusted certificates are managed in the web interface, in the "Administration" → "Trusted certificates" section.
For details, see [Trusted certificates](../trusted-certificates/).

## Audit logs

Audit logs record user actions and help control operations performed through the portal API.
Audit logs are generated by DDP Backend.

These logs are created automatically for HTTP requests to the API, except for `GET` requests and several requests listed in the [audit log documentation](../audit-logs/#audit-log-contents).
Each record contains information about the user, client IP address, endpoint, HTTP method, and response status.

Audit logs are stored in the PostgreSQL database and can be viewed in the portal web interface.
You can also export audit logs to CSV from the portal interface.
For details, see [Audit logs](../audit-logs/).

## HTTP security headers

DDP uses standard HTTP security headers to protect the web interface and API.
They are generated and applied by DDP Frontend and DDP Backend.
The headers reduce the risk of XSS and clickjacking attacks, prevent MIME sniffing, control referrer information, and enforce secure HTTPS connections.

The portal uses the following HTTP security headers:

- Content Security Policy (CSP).
- X-Frame-Options.
- X-Content-Type-Options.
- X-XSS-Protection.
- Referrer-Policy.
- Permissions-Policy.
- Strict-Transport-Security (HSTS).
  DDP Backend adds this header only if the TLS connection is terminated on DDP Backend itself.
  In a standard installation, the TLS connection is terminated on the Ingress controller, so HSTS is configured there.

The headers are configured in the `security.headers` parameter of the `development-platform` module: in the `development-platform` ModuleConfig (`spec.settings.security.headers`) or in the module settings in the Deckhouse web UI.
For details, see [HTTP security headers](../http-security-headers/).
