Шаблон (пакет шаблонов) — это версионированный набор файлов репозитория, опубликованный в OCI-реестре. Из шаблона создаётся новый микросервис, а когда в реестре появляется новая версия, DDP может обновить уже созданные сервисы.

{{< alert level="warning" >}}
Реестр шаблонов — экспериментальная функциональность. Формат пакета, состав настроек и API могут измениться в следующих выпусках.
{{< /alert >}}

Раздел находится в «Администрирование» → «Шаблоны» и содержит вкладки «Шаблоны», «Реестры», «Прогоны синхронизации» и «Настройки».

## Подключение реестра

На вкладке «Реестры» добавьте реестр и заполните поля:

- **«Название»** — уникальное название реестра.
- **«Реестр»** — хост реестра образов, например `registry.vendor.example`.
- **«Префикс репозиториев»** — префикс пути внутри реестра, например `ddp-templates`.
- **«Идентификаторы репозиториев»** — список отслеживаемых шаблонов. Поведение зависит от того, заполнен ли список:
  - пусто — DDP обходит каталог реестра: новые шаблоны появляются сами, а исчезнувший из реестра шаблон отзывается целиком;
  - список заполнен — каталог не запрашивается. Подходит для больших реестров и токенов без прав на листинг каталога, но новые шаблоны добавляются только вручную.
- **«Имя пользователя»** и **«Пароль»** — учётные данные реестра. Пароль хранится в зашифрованном виде и возвращается в API маской; оставьте маску без изменений, чтобы сохранить текущее значение.
- **«Пропускать проверку TLS»** — только для лабораторных сред и самоподписанных сертификатов.

Хост реестра проверяется при сохранении: адреса в петлевых, частных и link-local диапазонах отклоняются.

## Синхронизация

Синхронизация вытягивает из реестра список версий каждого отслеживаемого шаблона и обновляет галерею. Она запускается по расписанию и вручную кнопкой «Синхронизировать».

Каждая версия шаблона получает статус:

- **«доступна»** — версия пригодна к использованию;
- **«отозвана»** — версия скрыта из галереи администратором или исчезла из реестра;
- **«некорректна»** — пакет не прошёл проверку формата;
- **«недоступна»** — версия временно не читается из реестра.

Последняя доступная версия шаблона помечается как актуальная — именно её предлагает мастер создания микросервиса. Предварительные версии (например, `1.4.0-rc.1`) в галерее не предлагаются.

История запусков и их ошибки доступны на вкладке «Прогоны синхронизации».

Если один и тот же шаблон публикуется в нескольких реестрах, версию удерживает тот источник, который зарегистрировал её первым; остальные помечаются как конфликтующие. Версии шаблонов, чей реестр удалён, попадают в «осиротевшие» — их можно удалить одной кнопкой на вкладке «Шаблоны».

## Настройки

На вкладке «Настройки» задаются параметры синхронизации и автоматического обновления:

- **«Включить синхронизацию»** — включает периодическую синхронизацию и фоновую сверку версии шаблона с lock-файлом в репозитории сервиса.
- **«Интервал синхронизации»** и **«Интервал сверки версии шаблона»** — cron-выражения, например `*/15 * * * *`.
- **«Максимальный размер шаблона (килобайты)»** — шаблон больше лимита отклоняется при синхронизации.
- **«Ветка по умолчанию»** — ветка, в которую создаются репозитории новых сервисов.
- **«Префикс ветки обновления»** — префикс feature-ветки обновления; к нему добавляется версия. Смена префикса не учитывает уже открытые merge requests со старым префиксом.
- **«Лимит очереди обновлений»** — максимум постановок обновления в очередь за одну синхронизацию.
- **«Пользователь автоматизации»** — пользователь, от имени которого запускаются автоматические обновления. Пусто — автоматизация выключена.

{{< alert level="warning" >}}
Автоматические обновления выполняются с учётными данными выбранного пользователя автоматизации, и merge requests создаются от его имени. Выбирайте сервисного пользователя с минимально необходимыми правами в системе контроля версий.
{{< /alert >}}

## Создание микросервиса из шаблона

Раздел «Создать микросервис» на [главной странице](../home/overview/) проводит по шагам: выбор шаблона и версии, ввод названия и идентификатора сервиса, выбор системы и пространства в системе контроля версий, заполнение значений шаблона.

Значения шаблона описываются в самом пакете, поэтому набор полей отличается от шаблона к шаблону. Часть значений может подставляться автоматически из контекста запуска процесса — например, идентификатор системы или репозитория.

По завершении мастер запускает процесс каталога, привязанный к группе `create_microservice` в [правилах маппинга](../home/mapping-sets/#группы-процессов). Процесс создаёт репозиторий, рендерит в него файлы шаблона и записывает файл `.ddp/template.lock.yaml` с идентификатором и версией шаблона.

## Обновление сервиса

Файл `.ddp/template.lock.yaml` в репозитории сервиса — источник истины о том, на какой версии шаблона сервис находится. Когда в реестре появляется более новая версия, DDP предлагает обновление в карточке микросервиса, а при включённой автоматизации ставит его в очередь самостоятельно.

Обновление не пишет в основную ветку: оно создаёт feature-ветку с префиксом из настроек и открывает merge request. Если merge request для этой ветки уже открыт, повторный не создаётся.

Какие файлы затрагивает обновление, определяет стратегия, объявленная в пакете:

| Стратегия | Что делает |
|-----------|------------|
| `selective` | Перезаписывает только перечисленные пути |
| `additive` | Добавляет перечисленные пути, если их ещё нет |
| `selective_additive` | Перезаписывает одни пути и добавляет недостающие другие |
| `full` | Перезаписывает все файлы шаблона |
| `merge` | Выполняет трёхстороннее слияние перечисленных путей и добавляет недостающие |

Стратегию можно переопределить для конкретного сервиса свойством сущности. При конфликте слияния обновление прерывается целиком: репозиторий остаётся нетронутым, а процесс завершается ошибкой с указанием конфликтующих файлов.

## Авторам шаблонов

Пакет шаблонов — это каталог с манифестом `template.yaml`, описанием значений `values.yaml` и файлами репозитория. Файл `.templateignore` исключает пути из шаблонизации.

Для локальной работы в поставку входит утилита `ddp-template`: она проверяет пакет (`ddp-template lint`), рендерит его локально (`ddp-template render`) и публикует в реестр (`ddp-template publish`).

## Права доступа

- `read:template-packs` — просмотр галереи шаблонов и создание сервисов из них;
- `edit:template-packs` — отзыв, восстановление и удаление версий;
- `read:template-registries` — просмотр реестров, настроек и прогонов синхронизации;
- `edit:template-registries` — подключение и изменение реестров, изменение настроек, запуск синхронизации.
