{{< alert level="warning" >}}
MCP-сервер — функциональность на стадии Preview. Набор инструментов и API могут измениться в следующих выпусках без сохранения обратной совместимости.
{{< /alert >}}

MCP-сервер — компонент Deckhouse Development Portal (DDP, портала), который реализует протокол MCP (Model Context Protocol) и обеспечивает взаимодействие внешних AI-клиентов (таких как LM Studio, Claude Desktop и других) с порталом.
Сервер работает по JSON-RPC 2.0 и предоставляет набор инструментов для работы с ресурсами портала и проксирования запросов во внешние инфраструктурные сервисы.

MCP — это открытый протокол для взаимодействия AI-моделей с внешними системами. Подробнее о протоколе можно узнать на [официальном сайте MCP](https://modelcontextprotocol.io/).

{{< alert level="info" >}}
Все инструменты портала и подключённых серверов доступны через [MCP-коллекции](../mcp-management/#mcp-коллекции), к которым у пользователя есть доступ. Настройка MCP-серверов, пользовательских MCP-инструментов и коллекций выполняется в разделе [«Управление MCP»](../mcp-management/).
{{< /alert >}}

## Доступные инструменты

Инструменты портала включают операции API с префиксом `ddp_` и специализированные инструменты, перечисленные ниже. Любой инструмент требует включения в доступную пользователю MCP-коллекцию. Инструменты типа `external` доступны после [синхронизации каталога MCP-сервера](../mcp-management/#mcp-серверы) и [добавления инструментов в MCP-коллекцию](../mcp-management/#mcp-коллекции). Инструменты типа `custom` [создаются вручную](../mcp-management/#mcp-инструменты) в подразделе «MCP-инструменты» и доступны после добавления в MCP-коллекцию.

### Инструменты операций API

Имя инструмента операции имеет вид `ddp_<operationId>`. В «AI» → «MCP» → «Каталог» доступны описание операции и схема её аргументов. Инструменты объединены в группы, например «Каталог», «Действия», «Процессы и автоматизации» и «Рабочие пространства».

Примеры замены прежних имён:

| Прежнее имя | Актуальный инструмент |
| --- | --- |
| `get_resources` | `ddp_get_resources` |
| `get_resource_entities` | `ddp_get_resource_entities` |
| `get_entity` | `ddp_get_entity` |
| `get_entity_relations` | `ddp_get_entity_relations` |
| `get_actions` | `ddp_get_actions` |
| `get_datasources` | `ddp_get_datasources` |
| `get_external_services` | `ddp_get_external_services` |
| `get_process_instances` | `ddp_get_entity_process_history` |

При переносе интеграции обновите имя и прочитайте `inputSchema` из `tools/list`: аргументы соответствуют операции API и могут отличаться от прежнего инструмента. Специализированные `get_processes`, `run_process` и `get_process_instance` сохраняют собственные имена и параметры.

Результат инструмента операции содержит HTTP-статус, тип содержимого, способ кодирования и тело ответа. Например:

```json
{
  "status": 200,
  "contentType": "application/json; charset=utf-8",
  "encoding": "json",
  "body": []
}
```

Для JSON тело передаётся как JSON. Для остальных форматов используется `encoding: "base64"`. Проверяйте `status` и тело ответа, в том числе при отказе в доступе и ошибках проверки входных данных.

### get_external_data

Выполнить HTTP-запрос к внешнему сервису с учётными данными пользователя.

Параметры:

| Название                   | Тип    | Обязательность | Описание                                                               |
|----------------------------|--------|----------------|------------------------------------------------------------------------|
| `external_service_uuid`    | строка | Да         | UUID внешнего сервиса                                                  |
| `query`                    | строка | Да         | Описание запроса (например: «получить пайплайны проекта 123»)          |
| `api_path`                 | строка | Да         | Путь к API с параметрами запроса (например, пагинация)                 |
| `method`                   | строка | Нет            | HTTP-метод. По умолчанию: `GET`                                        |
| `body`                     | строка | Нет            | Тело запроса для POST/PUT/PATCH (JSON-строка)                          |

Учётные данные и заголовки берутся из настроек внешнего сервиса в портале.

Возвращает: результат HTTP-запроса к внешнему сервису.

Пример:

```text
Получи список проектов из внешнего сервиса GitLab
```

### get_processes

Получить список процессов с параметрами запуска.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `include_step_properties` | булево | Нет | Вернуть также задачи процесса, которые принимают собственные значения параметров действия. По умолчанию выключено |

Возвращает: для каждого процесса — UUID, идентификатор, название, описание, ресурсы, параметры запуска (`properties`) и пути контекста запуска, которые читает процесс (`contextPaths`). С `include_step_properties` — также задачи процесса с параметрами действий (`steps`). Схема элементов процесса не возвращается.

Пример:

```text
Получи список процессов
```

---

### get_service_templates

Получить шаблоны микросервисов из реестра шаблонов.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `include_all_versions` | булево | Нет | Вернуть все синхронизированные версии шаблонов. По умолчанию возвращается только текущая версия |

Возвращает: для каждого шаблона — `templateId`, `version`, `source`, название, описание, язык, признак текущей версии и параметры шаблона (`values`). Значения `templateId`, `version` и `source` передаются в контекст запуска процесса создания микросервиса как `context.template`.

Пример:

```sh
Получи список заготовок сервисов
```

### run_process

Запустить процесс для сущности.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `process_uuid` | строка | Да | UUID процесса |
| `entity_uuid` | строка | Да | UUID сущности ресурса, к которому привязан процесс |
| `properties` | объект | Да | Параметры запуска процесса: идентификатор параметра → значение. Не переданные параметры получают значения по умолчанию. Если задавать нечего, передайте `{}` |
| `context` | объект | Нет | [Контекст запуска](../admin/processes/overview/#контекст-запуска), доступный в шаблонах процесса как `.context` |
| `action_properties` | объект | Нет | Значения параметров действий задач: UUID задачи → объект «идентификатор параметра → значение». UUID задач и параметры возвращает `get_processes` с `include_step_properties` |
| `skipped_element_uuids` | массив | Нет | UUID элементов «AI-агент» и «Шаблон», которые пропускаются в этом запуске |
| `agent_provider_refs` | объект | Нет | AI-провайдеры для элементов «AI-агент»: UUID элемента → название провайдера |

Возвращает: сообщение о запуске и UUID созданного запуска процесса (`instanceUUID`).

Для сущности одновременно может выполняться только один запуск одного процесса: повторный запуск возвращает ошибку `409`.
Для запуска требуется разрешение `control:processes` на уровне портала, ресурса или сущности.

Пример:

```sh
Запусти процесс «Deploy» для сущности «api-gateway» с версией 1.4.0
```

### get_process_instance

Получить один запуск процесса с хранилищем.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `entity_uuid` | строка | Да | UUID сущности |
| `instance_uuid` | строка | Да | UUID запуска процесса из `ddp_get_entity_process_history` или из ответа `run_process` |
| `wait_seconds` | число | Нет | Сколько секунд ждать завершения запуска, не больше 45. Без параметра ответ возвращается сразу |

Возвращает: статус запуска, время, активные элементы и [хранилище процесса](../admin/processes/store/). Для статусов `Failed`, `Timeout` и `Partially Completed` ответ содержит поле `failureReason`: элемент, на котором произошла ошибка, итоговое сообщение и последние строки лога этого элемента.

Пример:

```sh
Покажи результат экземпляра процесса 3fa85f64-5717-4562-b3fc-2c963f66afa6
```

### Навыки

Инструменты чтения [навыков](../admin/ai-agents/skills/) передают инструкции и дополнительные файлы:

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `list_skills` | Необязательная строка `q` | Доступные пользователю навыки с описаниями и последними версиями |
| `get_skill` | Обязательный `name`, необязательный `version` | Текст `SKILL.md`, версия и список файлов |
| `get_skill_file` | Обязательные `name` и `path`, необязательный `version` | Текст дополнительного файла |

В обычном MCP-клиенте версия выбирается меткой; без неё используется последняя активная. В запуске агента доступ ограничен назначенными ему навыками и зафиксированными версиями. Бинарные файлы и файлы больше 1 МиБ через `get_skill_file` не читаются.

### Рабочие пространства

Инструменты позволяют подготовить [рабочее пространство](workspaces/) из чата:

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `get_workspace_templates` | Нет | Доступные шаблоны с активной версией, настройками репозитория и параметрами |
| `create_workspace` | Обязательные `template_uuid`, `name`, `ttl_hours`; необязательные `provider`, `repository_url`, `base_ref`, `entity_uuid`, `parameters` | Состояние созданного пространства; операция выполняется асинхронно |
| `get_workspace` | Обязательный `workspace_uuid`, необязательный `wait_seconds` до 45 | Статус, готовность, последняя ошибка и активная операция |
| `attach_workspace` | Обязательный `workspace_uuid` | Прикрепление пространства к текущему чату |

`provider` можно не передавать, когда подходящий провайдер уже задан в контексте чата. При вызове вне такого контекста укажите его явно. `parameters` — объект значений переменных шаблона; `ttl_hours` — целое число от 1 до 720.

`attach_workspace` работает только в контексте агента, отвечающего в чате портала. Используйте последовательность: получить шаблоны, создать пространство, дождаться готовности, прикрепить его к чату.

## Подключение MCP-сервера

### LM Studio

LM Studio 0.3.17 и новее поддерживает удалённые MCP-серверы. Серверы добавляются в файле `mcp.json`.

Чтобы подключить LM Studio к MCP-серверу портала:

1. В портале откройте «Профиль» и создайте API-токен.
1. В LM Studio откройте вкладку «Program» на правой боковой панели и выберите «Install» → «Edit mcp.json».
1. Добавьте MCP-сервер портала в объект `mcpServers`:

   ```json
   {
     "mcpServers": {
       "ddp": {
         "url": "https://<DOMAIN>/api/v2/mcp",
         "headers": {
           "Authorization": "Bearer <API_TOKEN>"
         }
       }
     }
   }
   ```

   Где:

   - `<DOMAIN>` — домен портала;
   - `<API_TOKEN>` — API-токен портала.

1. Сохраните файл.

После подключения модель может вызывать встроенные инструменты из раздела [«Доступные инструменты»](#доступные-инструменты) и инструменты из доступных вам MCP-коллекций. Все вызовы выполняются с вашими правами доступа.

### Подключение в других MCP-клиентах

MCP-сервер принимает запросы JSON-RPC 2.0 по HTTP. Для подключения клиента используйте следующие параметры:

- URL эндпоинта: `https://<DOMAIN>/api/v2/mcp`, где `<DOMAIN>` — домен портала.
- HTTP-метод: `POST`.
- Аутентификация: заголовок `Authorization: Bearer <API_TOKEN>`, где `<API_TOKEN>` — ваш API-токен портала из раздела «Профиль».

Сервер поддерживает следующие методы JSON-RPC:

- `initialize` — возвращает информацию о сервере и версию протокола `2024-11-05`;
- `tools/list` — возвращает список инструментов, доступных пользователю;
- `tools/call` — вызывает инструмент.

Другие методы возвращают ошибку `-32601` (`Method not found`).

### Пример запроса к MCP-серверу

HTTP-заголовки:

```text
Authorization: Bearer <API_TOKEN>
Content-Type: application/json
```

Тело запроса:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "ddp_get_resource_entities",
    "arguments": {
      "resource_uuid": "<RESOURCE_UUID>"
    }
  }
}
```

### Пример ответа от MCP-сервера

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"uuid\":\"...\",\"name\":\"Service 1\",\"properties\":{...}},...]"
      }
    ]
  }
}
```

## Безопасность

Аутентификация:

- Все запросы к MCP-серверу должны проходить аутентификацию с помощью API-токена из раздела «Профиль». Токен передаётся в заголовке `Authorization: Bearer <API_TOKEN>`.
- Права доступа соответствуют правам вашего пользователя в портале.

Права доступа:

- Инструменты работают с теми же правами, что и пользователь.
- `run_process`, `create_workspace`, `attach_workspace` и изменяющие операции `ddp_*` выполняют действия от имени пользователя. `get_external_data` также может отправить `POST`, `PUT`, `PATCH` или `DELETE` во внешний сервис.
- Если у вас нет доступа к ресурсу, инструмент вернёт ошибку доступа.
- Данные фильтруются в соответствии с вашими правами RBAC.

## Устранение неполадок

### Не удаётся подключиться к серверу

Если не получается подключиться к серверу:

- Проверьте правильность URL (должен заканчиваться на `/api/v2/mcp`).
- Убедитесь, что API-токен действителен.
- Проверьте, что портал доступен с вашего компьютера.
- Проверьте настройки файрвола и прокси.

### Ошибка аутентификации

Если не проходит аутентификация:

- Проверьте правильность формата токена.
- Убедитесь, что токен не истёк.
- Убедитесь, что используется заголовок `Authorization: Bearer <API_TOKEN>`.

### Инструмент возвращает ошибку доступа

Если при обращении к инструменту возвращается ошибка доступа:

- Убедитесь, что у вашего пользователя есть права на доступ к запрашиваемому ресурсу.
- Проверьте правильность названия или идентификатора ресурса.
- Обратитесь к администратору портала для проверки прав доступа.

### Данные не возвращаются

Если данные не возвращаются:

- Проверьте правильность параметров запроса.
- Убедитесь, что ресурс существует и содержит сущности.
- Проверьте логи портала для получения подробной информации об ошибке.
