{{< alert level="warning" >}}
Экспериментальный функционал
{{< /alert >}}

MCP-сервер — компонент Deckhouse Development Portal (DDP, портала), который реализует протокол MCP (Model Context Protocol) и обеспечивает взаимодействие внешних AI-клиентов (таких как LM Studio, Claude Desktop и других) с порталом.
Сервер работает по JSON-RPC 2.0 и предоставляет набор инструментов для работы с ресурсами портала и проксирования запросов во внешние инфраструктурные сервисы.

MCP — это открытый протокол для взаимодействия AI-моделей с внешними системами. Подробнее о протоколе можно узнать на [официальном сайте MCP](https://modelcontextprotocol.io/).

{{< alert level="info" >}}
Помимо встроенных инструментов портала, MCP-сервер может вызывать инструменты из [MCP-коллекций](../mcp-management/#mcp-коллекции), к которым у пользователя есть доступ. Настройка MCP-серверов, пользовательских MCP-инструментов и коллекций выполняется в разделе [«Управление MCP»](../mcp-management/).
{{< /alert >}}

## Доступные инструменты

Ниже перечислены **встроенные** инструменты портала. Инструменты типов `external` и `custom` доступны после [синхронизации каталога](../mcp-management/#mcp-серверы) и [добавления в MCP-коллекцию](../mcp-management/#mcp-коллекции).

### get_resources

Получить список ресурсов.

Параметры: нет.

Возвращает: список ресурсов.

Пример:

```sh
Получи список ресурсов
```

Пример:

```sh
Получи список внешних сервисов
```

### get_resource_entities

Получить все сущности выбранного ресурса.

Параметры:

| Название         | Тип    | Обязательность | Описание      |
|------------------|--------|----------------|---------------|
| `resource_uuid`  | строка | Да         | UUID ресурса  |

Возвращает: список сущностей ресурса.

Пример:

```sh
Получи все сервисы и покажи название и дату создания
```

Параметры:

| Название        | Тип    | Обязательность | Описание      |
|-----------------|--------|----------------|---------------|
| `entity_uuid`   | строка | Да         | UUID сущности |

Возвращает: данные одной сущности.

Пример:

```sh
Получи сущность с UUID 3fa85f64-5717-4562-b3fc-2c963f66afa6
```

### get_entity_relations

Получить связи сущности.

Параметры:

| Название         | Тип    | Обязательность | Описание               |
|------------------|--------|----------------|------------------------|
| `resource_uuid`  | строка | Да         | UUID ресурса           |
| `entity_slug`    | строка | Да         | Идентификатор сущности |

Возвращает: список связей сущности.

Пример:

```sh

```

### get_external_data

Выполнить HTTP-запрос к внешнему сервису с учётными данными пользователя.

Параметры:

| Название                   | Тип    | Обязательность | Описание                                                               |
|----------------------------|--------|----------------|------------------------------------------------------------------------|
| `external_service_uuid`    | строка | Да         | UUID внешнего сервиса                                                  |
| `query`                    | строка | Да         | Описание запроса (например: «получить пайплайны проекта 123»)          |
| `api_path`                 | строка | Да         | Путь к API с параметрами запроса (например, пагинация)                 |
| `method`                   | строка | Нет            | HTTP-метод. По умолчанию: `GET`                                        |
| `body`                     | строка | Нет            | Тело запроса для POST/PUT/PATCH (JSON-строка)                          |

Учётные данные и заголовки берутся из настроек внешнего сервиса в портале.

Возвращает: результат HTTP-запроса к внешнему сервису.

Пример:

```sh
Получи список проектов из внешнего сервиса GitLab
```

### get_actions

Получить список действий с описанием входных параметров.

Параметры: нет.

Возвращает: для каждого действия — UUID, идентификатор, название, описание, тип, признак подтверждения `approval`, привязанные ресурсы и параметры пользовательской формы. Для параметров типов Enum и List возвращаются варианты значений. Тело действия и настройки запроса не возвращаются.

Действие с `approval: true` при запуске ожидает подтверждения.

Пример:

```sh
Получи список действий
```

### get_processes

Получить список процессов с параметрами запуска.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `include_step_properties` | булево | Нет | Вернуть также задачи процесса, которые принимают собственные значения параметров действия. По умолчанию выключено |

Возвращает: для каждого процесса — UUID, идентификатор, название, описание, ресурсы, параметры запуска (`properties`) и пути контекста запуска, которые читает процесс (`contextPaths`). С `include_step_properties` — также задачи процесса с параметрами действий (`steps`). Схема элементов процесса не возвращается.

Пример:

```sh
Получи список процессов
```

### get_service_templates

Получить шаблоны микросервисов из реестра шаблонов.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `include_all_versions` | булево | Нет | Вернуть все синхронизированные версии шаблонов. По умолчанию возвращается только текущая версия |

Возвращает: для каждого шаблона — `templateId`, `version`, `source`, название, описание, язык, признак текущей версии и параметры шаблона (`values`). Значения `templateId`, `version` и `source` передаются в контекст запуска процесса создания микросервиса как `context.template`.

Пример:

```sh
Получи список заготовок сервисов
```

### run_process

Запустить процесс для сущности.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `process_uuid` | строка | Да | UUID процесса |
| `entity_uuid` | строка | Да | UUID сущности ресурса, к которому привязан процесс |
| `properties` | объект | Да | Параметры запуска процесса: идентификатор параметра → значение. Не переданные параметры получают значения по умолчанию. Если задавать нечего, передайте `{}` |
| `context` | объект | Нет | [Контекст запуска](../admin/processes/overview/#контекст-запуска), доступный в шаблонах процесса как `.context` |
| `action_properties` | объект | Нет | Значения параметров действий задач: UUID задачи → объект «идентификатор параметра → значение». UUID задач и параметры возвращает `get_processes` с `include_step_properties` |
| `skipped_element_uuids` | массив | Нет | UUID элементов «AI-агент» и «Шаблон», которые пропускаются в этом запуске |
| `agent_provider_refs` | объект | Нет | AI-провайдеры для элементов «AI-агент»: UUID элемента → название провайдера |

Возвращает: сообщение о запуске и UUID созданного запуска процесса (`instanceUUID`).

Для сущности одновременно может выполняться только один запуск одного процесса: повторный запуск возвращает ошибку `409`.
Для запуска требуется разрешение `control:processes` на уровне портала, ресурса или сущности.

Пример:

```sh
Запусти процесс «Deploy» для сущности «api-gateway» с версией 1.4.0
```

### get_process_instances

Получить запуски процессов сущности, новые первыми.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `entity_uuid` | строка | Да | UUID сущности |
| `process_uuid` | строка | Нет | Вернуть только запуски этого процесса |
| `status` | строка | Нет | Вернуть только запуски с этим статусом, например `Running` или `Completed` |
| `page` | число | Нет | Номер страницы, начиная с 1 |
| `per_page` | число | Нет | Число запусков на странице. По умолчанию — 10 |

Возвращает: список запусков процессов со статусом и временем создания.

Пример:

```sh
Идёт ли ещё какой-нибудь процесс по сущности «api-gateway»
```

---

### get_process_instance

Получить один запуск процесса с хранилищем.

Параметры:

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `entity_uuid` | строка | Да | UUID сущности |
| `instance_uuid` | строка | Да | UUID запуска процесса из `get_process_instances` или из ответа `run_process` |
| `wait_seconds` | число | Нет | Сколько секунд ждать завершения запуска, не больше 45. Без параметра ответ возвращается сразу |

Возвращает: статус запуска, время, активные элементы и [хранилище процесса](../admin/processes/store/). Для статусов `Failed`, `Timeout` и `Partially Completed` ответ содержит поле `failureReason`: элемент, на котором произошла ошибка, итоговое сообщение и последние строки лога этого элемента.

Пример:

```sh
Покажи результат экземпляра процесса 3fa85f64-5717-4562-b3fc-2c963f66afa6
```

## Подключение MCP-сервера

### LM Studio

1. Получение параметров:

   - Войдите в Deckhouse Development Portal.
   - Получите API-токен в разделе «Профиль».
   - Запишите URL портала (например, `https://ddp.example.com`).

1. Настройка в LM Studio:

   - Откройте LM Studio.
   - Перейдите в настройки (Settings).
   - Найдите раздел «MCP Servers» или «Model Context Protocol».
   - Нажмите «Add Server» или «Добавить сервер».

1. Конфигурация сервера (заполните следующие поля):

   - «Server Name»: `DDP MCP Server` (или любое удобное название).
   - «Server URL»: `https://<DOMAIN>/api/v2/mcp`.
   - «Transport»: `HTTP` или `JSON-RPC`.
   - «Authentication»:
     - «Type»: `Bearer Token` или аналог (заголовок `Authorization`).
     - «Header»: `Authorization: Bearer <ваш_api_токен>`.
     - «Token»: вставьте ваш API-токен портала (из раздела «Профиль»).

1. Проверка подключения:

   - Сохраните конфигурацию.
   - После сохранения конфигурации LM Studio подключится к серверу.
   - Если подключение успешно, вы увидите список доступных инструментов:
      - `get_resources` — получить список ресурсов.
      - `get_external_services` — получить список внешних сервисов (GitLab, SonarQube и т. д.).
      - `get_resource_entities` — получить все сущности выбранного ресурса.
      - `get_entity` — получить одну сущность по UUID.
      - `get_entity_relations` — получить связи сущности по ресурсу и идентификатору.
      - `get_external_data` — выполнить HTTP-запрос к внешнему сервису с учётными данными пользователя.
      - `get_actions` — получить список действий.
      - `get_datasources` — получить список источников данных.
      - `get_processes` — получить список процессов с параметрами запуска.
      - `get_service_templates` — получить шаблоны микросервисов.
      - `run_process` — запустить процесс для сущности.
      - `get_process_instances` — получить запуски процессов сущности.
      - `get_process_instance` — получить один запуск процесса с хранилищем.

После подключения вы можете использовать инструменты в диалогах с моделями.

Все вызовы выполняются с вашими правами доступа.

### Подключение в других MCP-клиентах

MCP-сервер Deckhouse Development Portal совместим с любыми клиентами, поддерживающими протокол MCP через JSON-RPC 2.0.

Общие шаги подключения:

1. «URL эндпоинта»: `https://your-platform.com/api/v2/mcp`.
1. «Протокол»: JSON-RPC 2.0.
1. «Аутентификация»:
   - Заголовок: `Authorization: Bearer YOUR_API_TOKEN`.
   - Где `YOUR_API_TOKEN` — ваш API-токен портала (раздел «Профиль»).
1. «Метод»: POST.

### Пример запроса к MCP-серверу

HTTP-заголовки:

```sh
Authorization: Bearer your-api-token-here
Content-Type: application/json
```

Тело запроса:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_resource_entities",
    "arguments": {
      "resource_uuid": "uuid-нужного-ресурса"
    }
  }
}
```

### Пример ответа от MCP-сервера

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"uuid\":\"...\",\"name\":\"Service 1\",\"properties\":{...}},...]"
      }
    ]
  }
}
```

## Запуск процесса из Coder

Если MCP-клиент Coder передаёт заголовки Coder (опция пересылки заголовков Coder), портал сохраняет их значения для процессов, запущенных инструментом `run_process`.
В шаблонах такого процесса значения доступны через корень `.caller`:

| Заголовок | Выражение |
|---|---|
| `X-Coder-Owner-Id` | `{{ .caller.owner_id }}` |
| `X-Coder-Chat-Id` | `{{ .caller.chat_id }}` |
| `X-Coder-Subchat-Id` | `{{ .caller.subchat_id }}` |
| `X-Coder-Workspace-Id` | `{{ .caller.workspace_id }}` |

При запуске процесса из интерфейса портала корень `.caller` пуст.

## Безопасность

Аутентификация:

- Все запросы к MCP-серверу должны проходить аутентификацию с помощью API-токена из раздела «Профиль». Токен передаётся в заголовке `Authorization: Bearer <api_token>`.
- Права доступа соответствуют правам вашего пользователя в портале.

Права доступа:

- Инструменты работают с теми же правами, что и пользователь.
- Инструменты `run_process` и `get_external_data` изменяют данные: первый запускает процесс, второй может выполнить запрос `POST`, `PUT`, `PATCH` или `DELETE` к внешнему сервису.
- Если у вас нет доступа к ресурсу, инструмент вернёт ошибку доступа.
- Данные фильтруются в соответствии с вашими правами RBAC.

## Устранение неполадок

### Не удаётся подключиться к серверу

Если не получается подключиться к серверу:

- Проверьте правильность URL (должен заканчиваться на `/api/v2/mcp`).
- Убедитесь, что API-токен действителен.
- Проверьте, что портал доступен с вашего компьютера.
- Проверьте настройки файрвола и прокси.

### Ошибка аутентификации

Если не проходит аутентификация:

- Проверьте правильность формата токена.
- Убедитесь, что токен не истёк.
- Убедитесь, что используется заголовок `Authorization: Bearer <api_token>`.

### Инструмент возвращает ошибку доступа

Если при обращении к инструменту возвращается ошибка доступа:

- Убедитесь, что у вашего пользователя есть права на доступ к запрашиваемому ресурсу.
- Проверьте правильность названия или идентификатора ресурса.
- Обратитесь к администратору портала для проверки прав доступа.

### Данные не возвращаются

Если данные не возвращаются:

- Проверьте правильность параметров запроса.
- Убедитесь, что ресурс существует и содержит сущности.
- Проверьте логи портала для получения подробной информации об ошибке.
